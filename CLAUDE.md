# Claude Code Assistant Instructions - Salesforce Data Treecipe

## AI Context & Project Overview

You are assisting with **Salesforce Data Treecipe**, a **VS Code extension** (TypeScript) that auto-generates fake-data recipe YAML files from Salesforce object metadata (source format). It supports two faker backends: **faker-js** (built-in, no setup) and **snowfakery** (external Python CLI). The extension bridges Salesforce source-format XML metadata → YAML recipe files → Salesforce Collections API datasets.

## Key Project Files

- `src/extension.ts` - VS Code extension entry point; registers all commands
- `src/treecipe/src/` - All core service logic (one folder per service)
- `src/treecipe/src/RecipeFakerService.ts/` - **Directory** (not a file) containing `FakerJSRecipeFakerService/` and `SnowfakeryRecipeFakerService/` implementations
- `src/treecipe/src/FakerRecipeProcessor/` - Interface + FakerJS and Snowfakery recipe processor implementations
- `src/treecipe/src/DirectoryProcessingService/` - Parses Salesforce object metadata XML directories
- `src/treecipe/src/RelationshipService/` - Groups objects into Treecipe files by relationship hierarchy
- `src/treecipe/src/RecipeService/` - Orchestrates recipe YAML file creation
- `package.json` - Extension manifest; all five commands declared under `contributes.commands`
- `jest.config.js` - Jest configuration (`ts-jest`, `jest-extended`)
- `CHANGELOG.md` - Feature history; read before starting work to understand recent changes

## Primary Objectives

1. **Follow existing service patterns** - Each service is a class in its own folder; tests live in a `tests/` subfolder alongside the service file
2. **Field-type-driven generation** - Recipe output is determined by Salesforce XML `<type>` tag; use `<precision>` and `<scale>` to constrain numeric/currency values
3. **Support both faker backends** - Every field-type handler must have equivalent implementations in both `FakerJSRecipeFakerService` and `SnowfakeryRecipeFakerService`
4. **Write tests first** - Every service has a `tests/` folder with Jest specs; add or update tests with every change

## Architecture Patterns

### Extension Command Flow

```
User runs command (Cmd+Shift+P)
  → extension.ts registers command → ExtensionCommandService handler
    → ConfigurationService reads treecipe.config.json
      → DirectoryProcessingService walks salesforceObjectsPath
        → XmlFileProcessor parses each field's XML
          → ObjectInfoWrapper wraps parsed metadata
            → RecordTypeService / ValueSetService / RelationshipService enrich data
              → RecipeService orchestrates YAML generation
                → FakerJSRecipeFakerService OR SnowfakeryRecipeFakerService
                  → generates faker expression per field type
                → Writes YAML recipe file(s) to workspace
```

### Key Design Decisions

- **`RecipeFakerService.ts` is a directory** — it contains both faker implementations as subfolders; this naming is intentional and must not be changed
- **Apex written into a user's project is `SDT`-prefixed** — every class in `apexPicklistDependencyFramework/SDTPicklistDependencyFramework/` (the framework source shipped in the .vsix and scaffolded into the user's package directory), and every class the generator emits, starts with `SDT` so it cannot collide with the user's own Apex. Keep new Apex consistent with this
- **Every picklist value reaches a recipe through its backend's escaper or `buildDependentPicklistChoiceItem`, never raw** — values come from metadata a repository author controls, and there are six sinks per backend: the default and record-type expressions, a dependent picklist's `when:` and its choices, a record type's dependent choices, and the TODO naming a controlling value. The expression escaper is per LANGUAGE (`escapePicklistValueForJavaScriptString(value, quote)` for faker-js, `escapePicklistValueForJinjaStringLiteral` for snowfakery); the YAML half is shared in `RecipeYamlScalar`, because PyYAML ends a line at U+0085, U+2028 and U+2029 where js-yaml does not, and a value is only inert if NEITHER parser sees a break. A dependent choice is a YAML item rather than an expression, so it stays plain when safe (`isSafeAsPlainScalar`: no structure, no template delimiter, and nothing YAML would read as a boolean, null or number — `Yes`/`No` came back as `True`/`False`) and is quoted otherwise. In snowfakery an item carrying a template delimiter is also written as a Jinja literal, because snowfakery renders a string in whichever of its environments the string's delimiters select, quoted or not — and its DEFAULT mode (`snowfakery_version` 2) has TWO: `${{`/`${%`, and a legacy, unsandboxed `<<`/`<%` one. Missing the second is how `<< … >>` in a picklist value executed a shell command in review. `renderWithSnowfakeryJinja` copies that compiler selection; keep it a copy of snowfakery's `JinjaTemplateEvaluatorFactory`, not a guess at it. `FakerJSRecipeProcessor.parseWhenCondition` is the inverse of the faker-js `when:` escaping; change the two together. `buildRecipeWithEveryPicklistSink` and `DirectoryProcessor.hostilePicklistValues.test.ts` hold every sink to the same payload list, so a new sink that skips the escaper fails there
- **A metadata NAME reaches a recipe only if it IS a Salesforce api name** — field `<fullName>`, record type `<fullName>` and `<controllingField>` all come from workspace XML, and a line break in any of them used to start a recipe line of its author's choosing, whose `${{ … }}` faker-js evaluates with `new Function()` (#120). There is one guard per NAME, not per sink: `appendFieldRecipeToObjectRecipe` is the single place a field KEY is written (OOTB entries, field files, record type line, compound components) and drops the value with a refused key, because a value can embed the same name; `partitionRecordTypesByWritableDeveloperName` splits record types where they are LOADED, so the header and every record-type line in both backends only ever see valid names; `getDependentPicklistRecipeFakerValue` refuses a controlling field before either backend's `when:` is built. A refused name becomes one `### TODO -- … SKIPPED` comment, escaped through `RecipeYamlScalar.escapeForComment`. Rejected rather than quoted: a quoted key is valid YAML but names a field no org can have. A refused dependent picklist's value is that comment, so it loads as `null` — which is why `FakerJSRecipeProcessor` checks for a non-null OBJECT before `'if' in`. A new name that reaches a recipe, or a new sink for one of these three that bypasses its guard, re-opens the hole. OBJECT names are guarded at the one door into the map: `ObjectInfoWrapper.addKeyToObjectInfoMap` refuses anything that is not an api name, records it in `SkippedObjectApiNames` (absent when nothing was refused) and returns `false`, and `DirectoryProcessor` warns once after the walk (#164). That warning goes through `escapeForNotification`, which escapes `[`, `]`, `(` and `)` as well as line breaks: a VS Code notification renders `[label](command:…)` as a link that RUNS the command, so any workspace text shown in one needs the same treatment. A directory name and a lookup's `<referenceTo>` or relationship mapping both reach it, so a caller that adds an object any other way, or indexes the map with a name it did not get `true` for, re-opens the hole. The rule itself is `SalesforceApiName`, which imports NOTHING because `ObjectInfoWrapper`, `SOQLTemplateService` and `MermaidService` run without vscode; `SOQLTemplateService` leaves out every field, record type and `<referenceTo>` it refuses, and `MermaidService` every field, so both markdown files agree with the recipe. Insert resolves a nickname to the FIRST record holding it, and an entry with `count > 1` and no friends gives every record one nickname, so only for an entry a reference names those records are renamed `<nickname>_<n>`, skipping names already held — a data set nothing names is written exactly as before. Those records have no friends, which is what makes renaming them safe; a change that renames a record with friends breaks every child's ancestor reference. An object with a SELF-lookup gets ONE more friend, last in its `friends:` block: itself again, nicknamed `<Object>_child_NickName`, every self-lookup wired to the iteration above because it is passed as its own ancestor, and carrying no friends of its own, so nothing recurses (#188). That puts a parent and its child in one `collectionsApi-<Object>.json`, which is why `CollectionsApiService.partitionRecordsIntoInsertRounds` inserts a file in rounds: a record naming another record of the SAME file waits for the round that inserts it, and a file with no such reference is one round, the request it always was. The Recipe Cockpit tells two occurrences of one object apart by NICKNAME, never by api name: the scan records `nicknames` and `parentHeaderIndex`, `parseRecipeSource` keeps a later occurrence as an `iterations` entry on the first only when each carries a nickname no other occurrence does (else first-wins, as before), and every writer operation takes an optional `objectNickname`; without one, an object written twice is still refused. A tree where nothing nests goes through `buildCombinedTreeRecipe` unchanged, byte for byte. Two consumers make the wiring true at run time and both must stay: `FakerJSRecipeProcessor` hands each friend a `Map` of every ancestor's YAML nickname to the nickname of the record it is generated under (not only the direct parent's — with `count > 1` a grandchild's top-parent lookup would otherwise name no record), and `CollectionsApiService.updateLookupReferencesInCollectionApiJson` replaces a JSON string only when the WHOLE string is a nickname, because a friend's generated nickname CONTAINS its parent's (`Contact_Account_NickName`) and a substring replace rewrote the friend's own `referenceId`. The DirectoryProcessor suites load `objectInfoWrapper.RecipeFiles` — what is written — and `generatedRecipeYaml` holds every nested object to the flat recipe's fields apart from the wired lookups

- [ ] Read the relevant service file(s) before making changes
- [ ] Add or update tests in the service's `tests/` folder
- [ ] If adding a new Salesforce field type handler, implement it in **both** `FakerJSRecipeFakerService` and `SnowfakeryRecipeFakerService`
- [ ] Add XML fixture files to `tests/mocks/` if the change depends on specific XML markup
- [ ] Run `npm run jest-test` — all tests pass, coverage does not regress
- [ ] Run `npm run compile` — zero TypeScript errors
- [ ] Run `npm run lint` — zero ESLint errors
- [ ] Update `CHANGELOG.md` with the change under an appropriate version heading

## Common Tasks

### Adding a New Salesforce Field Type Handler

1. Identify the Salesforce `<type>` value (e.g., `"Checkbox"`, `"Date"`)
2. Add a handler in `FakerJSRecipeFakerService.ts` that returns the appropriate faker-js expression
3. Add the equivalent handler in `SnowfakeryRecipeFakerService.ts`
4. Add tests for both in their respective `tests/` folders, with sample XML in `mocks/`

### Adding a New VS Code Command

1. Declare it in `package.json` under `contributes.commands`
2. Register it in `extension.ts`
3. Implement the handler in `ExtensionCommandService.ts`
4. Wrap in `ErrorHandlingService` for consistent error reporting

## Remember

- **Both faker backends** - New field type handlers must be implemented in both FakerJS and Snowfakery services
- **Tests first** - Add/update tests in the service's `tests/` folder before or alongside code changes
- **No comments for obvious code** - Only comment where logic is genuinely non-obvious
- **`RecipeFakerService.ts` is a directory** - Do not confuse it with the `.ts` file of the same name in the parent folder
- **Precision/scale math** - `left_digits = precision - scale`; `max = 10^left_digits - 1`; `dec = scale`
- **Special characters in picklists** - Always escape before embedding in faker expression strings
