# Claude Code Assistant Instructions - Salesforce Data Treecipe

## AI Context & Project Overview

You are assisting with **Salesforce Data Treecipe**, a **VS Code extension** (TypeScript) that auto-generates fake-data recipe YAML files from Salesforce object metadata (source format). It supports two faker backends: **faker-js** (built-in, no setup) and **snowfakery** (external Python CLI). The extension bridges Salesforce source-format XML metadata → YAML recipe files → Salesforce Collections API datasets.

## Key Project Files

- `src/extension.ts` - VS Code extension entry point; registers all commands
- `src/treecipe/src/` - All core service logic (one folder per service)
- `src/treecipe/src/RecipeFakerService.ts/` - **Directory** (not a file) containing `FakerJSRecipeFakerService/` and `SnowfakeryRecipeFakerService/` implementations
- `src/treecipe/src/FakerRecipeProcessor/` - Interface + FakerJS and Snowfakery recipe processor implementations
- `src/treecipe/src/DirectoryProcessingService/` - Parses Salesforce object metadata XML directories
- `src/treecipe/src/RelationshipService/` - Groups objects into Treecipe files by relationship hierarchy
- `src/treecipe/src/RecipeService/` - Orchestrates recipe YAML file creation
- `package.json` - Extension manifest; all five commands declared under `contributes.commands`
- `jest.config.js` - Jest configuration (`ts-jest`, `jest-extended`)
- `CHANGELOG.md` - Feature history; read before starting work to understand recent changes

## Primary Objectives

1. **Follow existing service patterns** - Each service is a class in its own folder; tests live in a `tests/` subfolder alongside the service file
2. **Field-type-driven generation** - Recipe output is determined by Salesforce XML `<type>` tag; use `<precision>` and `<scale>` to constrain numeric/currency values
3. **Support both faker backends** - Every field-type handler must have equivalent implementations in both `FakerJSRecipeFakerService` and `SnowfakeryRecipeFakerService`
4. **Write tests first** - Every service has a `tests/` folder with Jest specs; add or update tests with every change

### Testing Requirements

- **Tests are mandatory** - Run `npm run jest-test` after EVERY code change
- **Update tests each change** - When modifying any service, add or update the corresponding test file in its `tests/` folder
- **Tests must pass before committing** - Never commit code with failing tests
- **Test coverage grows with features** - Every new feature, bug fix, or refactor must include relevant test updates

- Use Jest `describe`/`it` or `describe`/`test` blocks; use `jest-extended` matchers where appropriate
- `restoreMocks: true` is set globally — do not manually restore mocks between tests
- **Never replace a Node core module function by assignment** (`fs.promises.readdir = jest.fn()`); always use `jest.spyOn`. `restoreMocks` restores only what `jest.spyOn` registered, and a core module is shared by every suite in a worker rather than rebuilt with the module registry, so an assignment leaks into whichever suite jest schedules next. `jestSetup/CoreModuleIsolation.ts` puts such a replacement back after every test — it is a net, not a licence. Its `afterEach` runs BEFORE a test file's own root-level `afterEach` (root-block hooks run in declaration order, and setup files are evaluated first), so a file-scope `afterEach` cannot assert on an `fs` spy

- **TypeScript strict** - No implicit `any`; always define types/interfaces

- **Interface-first for faker services** - Both faker backends implement `IRecipeFakerService` and `IFakerRecipeProcessor`
- **No hard-coded Salesforce field values** - All field type mappings must be driven by the XML `<type>` value
- **Naming conventions** - PascalCase for classes/interfaces, camelCase for methods/variables; service files match their class name
- **No comments for self-evident code** - Only add comments where the logic is non-obvious

## Architecture Patterns

### Extension Command Flow

```
User runs command (Cmd+Shift+P)
  → extension.ts registers command → ExtensionCommandService handler
    → ConfigurationService reads treecipe.config.json
      → DirectoryProcessingService walks salesforceObjectsPath
        → XmlFileProcessor parses each field's XML
          → ObjectInfoWrapper wraps parsed metadata
            → RecordTypeService / ValueSetService / RelationshipService enrich data
              → RecipeService orchestrates YAML generation
                → FakerJSRecipeFakerService OR SnowfakeryRecipeFakerService
                  → generates faker expression per field type
                → Writes YAML recipe file(s) to workspace
```

### Key Design Decisions

- **`RecipeFakerService.ts` is a directory** — it contains both faker implementations as subfolders; this naming is intentional and must not be changed
- **Apex written into a user's project is `SDT`-prefixed** — every class in `apexPicklistDependencyFramework/SDTPicklistDependencyFramework/` (the framework source shipped in the .vsix and scaffolded into the user's package directory), and every class the generator emits, starts with `SDT` so it cannot collide with the user's own Apex. Keep new Apex consistent with this
- **Every picklist value reaches a recipe through its backend's escaper or `buildDependentPicklistChoiceItem`, never raw** — values come from metadata a repository author controls, and there are six sinks per backend: the default and record-type expressions, a dependent picklist's `when:` and its choices, a record type's dependent choices, and the TODO naming a controlling value. The expression escaper is per LANGUAGE (`escapePicklistValueForJavaScriptString(value, quote)` for faker-js, `escapePicklistValueForJinjaStringLiteral` for snowfakery); the YAML half is shared in `RecipeYamlScalar`, because PyYAML ends a line at U+0085, U+2028 and U+2029 where js-yaml does not, and a value is only inert if NEITHER parser sees a break. A dependent choice is a YAML item rather than an expression, so it stays plain when safe (`isSafeAsPlainScalar`: no structure, no template delimiter, and nothing YAML would read as a boolean, null or number — `Yes`/`No` came back as `True`/`False`) and is quoted otherwise. In snowfakery an item carrying a template delimiter is also written as a Jinja literal, because snowfakery renders a string in whichever of its environments the string's delimiters select, quoted or not — and its DEFAULT mode (`snowfakery_version` 2) has TWO: `${{`/`${%`, and a legacy, unsandboxed `<<`/`<%` one. Missing the second is how `<< … >>` in a picklist value executed a shell command in review. `renderWithSnowfakeryJinja` copies that compiler selection; keep it a copy of snowfakery's `JinjaTemplateEvaluatorFactory`, not a guess at it. `FakerJSRecipeProcessor.parseWhenCondition` is the inverse of the faker-js `when:` escaping; change the two together. `buildRecipeWithEveryPicklistSink` and `DirectoryProcessor.hostilePicklistValues.test.ts` hold every sink to the same payload list, so a new sink that skips the escaper fails there
- **A metadata NAME reaches a recipe only if it IS a Salesforce api name** — field `<fullName>`, record type `<fullName>` and `<controllingField>` all come from workspace XML, and a line break in any of them used to start a recipe line of its author's choosing, whose `${{ … }}` faker-js evaluates with `new Function()` (#120). There is one guard per NAME, not per sink: `appendFieldRecipeToObjectRecipe` is the single place a field KEY is written (OOTB entries, field files, record type line, compound components) and drops the value with a refused key, because a value can embed the same name; `partitionRecordTypesByWritableDeveloperName` splits record types where they are LOADED, so the header and every record-type line in both backends only ever see valid names; `getDependentPicklistRecipeFakerValue` refuses a controlling field before either backend's `when:` is built. A refused name becomes one `### TODO -- … SKIPPED` comment, escaped through `RecipeYamlScalar.escapeForComment`. Rejected rather than quoted: a quoted key is valid YAML but names a field no org can have. A refused dependent picklist's value is that comment, so it loads as `null` — which is why `FakerJSRecipeProcessor` checks for a non-null OBJECT before `'if' in`. A new name that reaches a recipe, or a new sink for one of these three that bypasses its guard, re-opens the hole. OBJECT names are guarded at the one door into the map: `ObjectInfoWrapper.addKeyToObjectInfoMap` refuses anything that is not an api name, records it in `SkippedObjectApiNames` (absent when nothing was refused) and returns `false`, and `DirectoryProcessor` warns once after the walk (#164). That warning goes through `escapeForNotification`, which escapes `[`, `]`, `(` and `)` as well as line breaks: a VS Code notification renders `[label](command:…)` as a link that RUNS the command, so any workspace text shown in one needs the same treatment. A directory name and a lookup's `<referenceTo>` or relationship mapping both reach it, so a caller that adds an object any other way, or indexes the map with a name it did not get `true` for, re-opens the hole. The rule itself is `SalesforceApiName`, which imports NOTHING because `ObjectInfoWrapper`, `SOQLTemplateService` and `MermaidService` run without vscode; `SOQLTemplateService` leaves out every field, record type and `<referenceTo>` it refuses, and `MermaidService` every field, so both markdown files agree with the recipe. Error notifications get it CENTRALLY: `ErrorHandlingService.handleGenericError` escapes `error.message` and `handleMissingTreecipeConfigSetup` the stale-setting notice, because an error message can quote workspace text (a `js-yaml` parse error quotes the recipe line) and every `handleCapturedError` caller lands there (#186). The Report Issue URL keeps the RAW text, and `escapeForNotification` is idempotent on its own output, so an already-escaped notice is not doubled.
- **A map keyed by picklist VALUES has no prototype** — a value can be `constructor`, `toString` or `__proto__`, and a `{}` map reads the inherited member back (`push is not a function`, `not iterable`) or, on `__proto__`, replaces the prototype and loses the value. Build such a map with `Object.create(null)` and test membership with an own-key check, never `in` (#160). `DirectoryProcessor.prototypeNamedPicklistValues.test.ts` runs every one of those names through both backends and the spec generator
- **Both faker backends must stay in sync** — whenever a new field type handler is added to `FakerJSRecipeFakerService`, add the equivalent to `SnowfakeryRecipeFakerService`
- **Numeric/currency precision** — `<precision>` (total digits) and `<scale>` (decimal places) from XML drive `max` and `dec` parameters; `left_digits = precision - scale`
- **Picklist handling** — special characters (`&`, `'`, etc.) in picklist values must be escaped before embedding in faker expressions
- **A record type's picklist variant is a COMMENTED line** — a picklist or multi-select picklist with record-type values is written as its default expression, then per record type a `### TODO` and `# ${{ … }}`. A bare expression indented under a field's value is not YAML, and Run Faker by Recipe loads the WHOLE file, so one such line failed every object in the recipe in both backends (#153). `DirectoryProcessor.generatedRecipeYaml.test.ts` loads every file the real pipeline writes, with each backend, so anything else generation emits is held to the same bar. `RecordTypeId` follows the same rule: its value is ONE developer name, the first ACTIVE record type (the first if none is), and each other is a `# Obj.DeveloperName` line under its TODO — a bare name on the next line folds into the value, and the insert's Id swap then sends several Ids in one field (#157). One record type gets no TODO. "First" is a fixed order: `getRecordTypeToApiFieldToRecordTypeWrapper` sorts by developer name with `<`, never `localeCompare`, ONCE where record types are loaded, because `readDirectory` lists in the file system's order and that decided the inserted record type and every record-type section in both backends (#166). A consumer that re-sorts, or a second loader that skips the sort, makes a recipe depend on the machine again
- **The generated Apex test suite is the published handle, and regeneration MERGES it** — `SDTPicklistDependencyTests.testSuite-meta.xml` is what `--suite-names`, Setup and `Run Picklist Dependency Check` all address, so nothing downstream depends on the generated class name. Unlike the `.cls` files it is NOT owned outright: a suite is a grouping a team curates, so generation unions its member in and removes nothing, and a file it cannot parse as an `ApexTestSuite` is left exactly as it is with a warning. The suite lives in a `testSuites` sibling of the classes directory — one derivation, in `getTestSuitesDirectoryPath`, so the two cannot drift off `main/default` separately. Its file name ends in `-meta.xml` without being a sidecar, which is why report filtering keys on `.cls-meta.xml`
- **The deployed-check asks about suite MEMBERSHIP, never suite existence** — a suite whose member class was deleted still exists, and `--suite-names` against it runs zero tests and reports success. One Tooling API query over `TestSuiteMembership` answers both halves; anything cheaper is a green check that verified nothing
- **The transpose is the writeback's whole reason to exist** — a validator failure is indexed by *controlling* value (`cle @ missing [plant]`) while `valueSettings` is indexed by *dependent* value (`plant ← cle`), so acting on a failure by hand means editing a block the message never names. `PicklistDependencyMetadataWriterService` owns that direction; keep it one function with one direction
- **Anything spanning a run is keyed by object AND field** — a run reconciles every per-object spec class at once, and field api names repeat across objects (`Status__c` on Account and on Case). `PicklistDependencyMetadataWriterService.buildFieldKey` is the one place that shape is defined; use it for every path map, dependency-graph key and report line rather than the bare field api name
- **Writeback merges intent, it does not substitute for it** — a spec asserts what a controlling value must and must not unlock; anything it names neither way it makes no claim about. Only `expectNone` and `expectExactly` are exhaustive and may remove. Reading silence as deletion would let a one-line spec strip a file
- **The spec manifest is the single source for the Explorer** — `Generate Picklist Dependency Tests` emits the Apex classes and `treecipe/PicklistDependencySpecs/manifest.json` from one in-memory model in one run, and the Explorer renders the manifest rather than re-walking the source XML. Anything that changes what the generator emits must flow through the manifest too, or the panel and the Apex become two derivations again. The manifest never goes in a package directory — a stray `.json` there breaks `sf project deploy`
- **The manifest records the information content of the specs, not their cross product** — what a controlling value must NOT unlock is the complement of what it unlocks within the field's declared values, so recording it per expectation grew `manifest.json` with *combinations x declared values* (315.7 MB, a 1.4 s parse, ~59% of an Explorer open). A field entry carries `declaredValues` ONCE and an expectation carries `forbiddenValuesAreDeclaredComplement`; `buildSpecDetailsByManifest` reconstructs the array on read so every consumer — the Explorer's rows, and `PicklistDependencyMetadataWriterService`, whose transpose REMOVES pairs by that list — is unchanged. The marker is DERIVED AND COMPARED before it is recorded, never assumed: a forbidden set that is not the complement is written out literally, which is what makes the round trip a property rather than a coincidence of the two current generators. Three states stay distinct because the panel renders them differently — the marker, a written-out list (`expectNone` and `expectUnavailable` assert an EMPTY set against a non-empty universe), and neither, which asserts only the positive half. The universe is the one the spec was drawn against, so a record-type-scoped field records what the RECORD TYPE assigns; and it must be COMPLETE, per the complement rule above. Order it once per FIELD (`buildOrderedDeclaredValues`) rather than inside each complement — that was measured at 594 ms against 59 ms and would have handed back most of the parse saving
- **Recording a complement as a marker makes the manifest DECOMPRESSIVE, so reading it is bounded by what it expands to** — the file carries the sum of the two picklists while reading materializes their product, and that expansion happens on load, BEFORE `applyModelLimits`, which bounds what is rendered from a finished view model rather than what building one allocates. Under version 2 a forty-million-value expansion needed a ~400 MB file; now a 0.70 MB one does it. `countReconstructedDeclaredValues` counts what the MARKER expands (a literal forbidden list already costs the file what it costs memory) and a manifest past `maximumReconstructedDeclaredValues` is reported unreadable. That ceiling is MEASURED — 25 M is 4.3x the largest real org (1,200 fields reconstruct 5.7 M in 268 ms / 61 MB) and holds the load near 260 MB — and a test asserts the headroom rather than trusting the comment. And a universe read from disk is COMPLETE OR NOTHING: filtering `declaredValues` to the strings that parse leaves a list that looks whole, and every complement drawn from it understates what the spec forbids — one bad element would narrow the universe for every expectation on the field, where version 2 lost one expectation's list
- **The Explorer bounds what it renders, and never re-labels what it drops** — an object's rows are built on first expand, and `applyModelLimits` caps five axes plus one TOTAL budget (`maxRenderedCombinations`). The total is the part that bounds the payload: the per-axis caps only shape the panel, and their product is millions of rows. Bounding it took three axes, not one — combinations, dependent picklists per object, and `declaredValues`, which grows with a field's picklist rather than with how many combinations survive and was the dominant term once the others were capped. What SURVIVES a cap is MANIFEST ORDER — the first that fit, on every axis, including the total budget, which is spent in document order. That rule is asserted rather than left implicit: the panel used to retain rows a check had reported a failure for, and with no check to read there is no property of a row left to prefer by. Inventing one (longest, most combinations, alphabetical) would order the panel by something the generated Apex does not, and an unasserted order is one a refactor can turn into "whatever the iteration produced" — at which point a reader cannot tell a dropped row from a moved one. The single exception retains an object carrying a SKIPPED FIELD, which is a fact about the metadata rather than about a run. A dropped row is ABSENT and counted in a notice, never rendered as something it was not — and the notice has to be TRUE of the axis it describes: the node cap is applied to ROOT CHAINS and a surviving chain brings every field beneath it, so an object can render far more fields than `maxNodesPerObject`, and every holder the TOTAL budget empties increments its own `truncatedCombinationCount` rather than only the aggregate. A field emptied silently renders as a field that declares no combinations, which is the same false claim one level down. Filtering works the same way: it hides, and recomputes nothing. Whenever a cap is added or changed, RE-MEASURE — the numbers in CHANGELOG 3.7.0 come from serializing synthetic models through the real builder, and two earlier drafts of this ceiling were chosen by reasoning and were wrong by 5-13x
- **The panel answers a value query itself, from what it was already sent** — "what does `Canada` unlock" is a question about rows, and the tree is indexed by the DEPENDENT field, so one controlling field's effects sit in sibling nodes nothing composes. `renderControllingValueSummary` composes them, and the filter narrows to ROWS rather than stopping at nodes. Both are derived IN THE PANEL from `allowedValues` the model already carries, so the posted payload is unchanged — a test pins that no `searchText` in it names a dependent value. Each matches only what its tab draws: Structure (`applyStructureFilter`) against ONE lowercased haystack per field (`searchTextOf`: names, label, controlling field and faker expression, shared by every occurrence of an object) plus the sized type the row draws; Data-by-Org (`applyDataFilter`) object names and, once compared, the names of the fields that differ; Previous Versions the run folder name (drawn on the row as `treeVersionFolder`) and date; Previous Fake Sets the data set folder name. Structure and Data-by-Org never hide an object (one with no match stays collapsed with "no matching fields"/"no matches") and auto-expand under the `RECIPE_COCKPIT_AUTO_EXPAND_*` limits, spent PER SEARCH BOX (`expandMatchesWithinBudget`); the history tabs hide the rows that do not match and count what is left. A search never switches the tab it was typed in. The panel's own name-keyed maps (`objectsByApiName`, `pendingPicklistValueElements`) are `Object.create(null)`, because an object named `__proto__` in a hand-edited wrapper otherwise vanished from its card. Tree DOM uses its own class names (`treeCard`, `treeObject`, `treeField`, …); the comparison's (`describeInOrg`, `statusFilter`, `orgStatus`, `orgProgress`, `diffBadge`, `objectDiff`, `orgDescribeStatus`, `regenerateRecipe`) are the Classic list's names, now drawn only inside a card's Data-by-Org tab. There is no view switch: a card's tabs are `RECIPE_COCKPIT_TREE_TABS` — Structure · Data-by-Org · Previous Versions · Previous Fake Sets, Structure selected, the history tabs only for a card with a history — and a `focusTree` can name any of them (a Create reloads onto `dataByOrg`; `readTreeFocus` still accepts only the history tabs from the panel)
- **Data-by-Org names an org only by INDEX, and counts only what the rendered trees list** — ONE org picker (select, type label, ⟳) sits in the toolbar and serves every card's Data-by-Org tab (#217); a selection's counts are held panel-wide (`dataOrgCountsByObject`) and drawn into each tab when it is built, so one `selectDataOrg` recounts every tab, built or not.  the host posts the authorized orgs as LABELS (`dataOrgList`); the panel posts back `selectDataOrg {orgIndex}`, an integer index into the list the host holds (`dataOrgDetails`), so no username or alias ever comes from the panel and none is posted to it. The objects counted are `collectDataOrgObjectApiNames` of the confirmed-drawn model (`dataOrgObjectApiNames`, pending/active like the other allow-lists: promoted on `rendered`, emptied on `ready`, a new post and a failure to draw). Listing orgs asks the CLI which orgs are connected (`sf org list --json --verbose`, which pings each authorized org's token), once per session or per ⟳ — see the connected-orgs bullet; the extension itself contacts an org only once one is selected, and the panel asks (`loadDataOrgs`) the first time any card's Data-by-Org tab opens or the toolbar's picker (`dataOrgLoad`) is used, never on panel open, and again for each later model once it has (`isDataOrgPickerInUse`) — so the org remembered in `context.workspaceState` (`RECIPE_COCKPIT_DATA_ORG_STATE_KEY`, keyed by USERNAME) is preselected on reopen without a connection, and one no longer authorized is forgotten silently. Every selection bumps `dataOrgRequestSequence`; `selectDataOrg` re-checks it (and the model) before every post and as the count's cancellation, a new model or a `ready` bumps it too, and the panel drops a message for an older `requestSequence` or `renderSequence`. `SalesforceOrgService.countRecords` mirrors `describeObjects`: `isUsableObjectApiName` before any query (the name is interpolated into SOQL), five in flight, successes cached by username and object, a connection failure thrown once for the whole org. The org type is `queryOrganizationType`, which answers undefined rather than guessing — anything that needs "is a sandbox" treats undefined as NO. **Data-by-Org never connects to production**, held twice: the toolbar picker lists only `SalesforceOrgService.listDataOrgDetails` — authorizations `isKnownNonProductionAuthorization` accepts (`isScratchOrg`/`isSandbox` exactly `true`, or a sandbox instance host; the CLI records `isSandbox` only when the production org is authorized too, so the host is read as well) — and posts how many it left out; and after connecting, an org whose Organization row is not `IsSandbox: true` (or did not answer) is asked NOTHING more — no count, no describe — and its readiness is refused for every object. Insert Data Set by Directory deliberately does not use this listing, and Compare uses it only to find the org Data-by-Org remembers: with none picked, Compare's quick pick lists every authorized org, because a describe writes nothing
- **Every org picker lists only what the Salesforce CLI reports CONNECTED, and fails closed** (#201) — Data-by-Org, Compare with an org…, Insert Data Set by Directory and Run Picklist Dependency Check all read `SalesforceOrgService.listConnectedOrgAuthorizations()`, which runs `sf org list --json --verbose` through `PicklistDependencyCheckService.runSalesforceCli` (the picklist check's invocation, with a timeout; never `--skip-connection-status`, never `logout`/`delete`). The timeout is `runSalesforceCli`'s OWN timer, never execFile's `timeout` option: on Windows the CLI is `cmd.exe`'s grandchild, execFile's timeout kills only `cmd.exe`, and its callback then waits on pipes the orphaned `node` still holds. So a timeout resolves at once as `timedOut` and `killProcessTree` ends the tree (`taskkill /pid <pid> /T /F`, no shell), as a cancellation also does and caches the parsed answer for the extension host's life. Two pickers during one check share its process; a FAILURE is never cached; `refreshConnectedOrgAuthorizations` (Data-by-Org's ⟳, and an org the extension creates) replaces the answer, sharing a check already in flight rather than starting a second process, and a generation bump keeps a check started before a clear from writing over it. The cache records the authorization usernames read BEFORE the CLI ran (`checkedAuthorizationUsernames`): an authorization added since is asked about again rather than reported not connected, and a quick pick (no ⟳) that a cached answer leaves empty asks again once — otherwise the warning's own advice, `sf org login web` and try again, could never work. CLI text shown in a notification goes through `escapeForNotification`. The JSON is untrusted: a non-scratch org is usable only on `connectedStatus === "Connected"`. A scratch org is never pinged by the CLI (it asks the Dev Hub), so it needs `status === "Active"` and `isExpired !== true` instead, and a `connectedStatus` only if it carries one. Requiring `connectedStatus` there would hide every scratch org. Anything else, a mistyped field or an org the answer does not name included, is left out with a reason (`expired`, `deleted`, `notConnected`), and an unusable entry outvotes a Connected one for the same username. Only surviving usernames are matched against `AuthInfo.listAllAuthorizations()`, and the existing filters apply on top. When the CLI cannot answer, NOTHING is listed (`OrgConnectionStatusUnavailableError`), never every authorization unchecked. Quick picks go through `VSCodeWorkspaceService.promptForAuthenticatedOrgDetailOnceListed`, which opens busy with nothing selectable until the listing answers. Data-by-Org drops its list and selection BEFORE a check, so nothing can be selected or created in mid-check, and a stale answer is discarded by `dataOrgRequestSequence`. Insert Data Set's free-text alias box is gone: it is a picker like the others
- **Create reaches only a SANDBOX, and every guard fails closed** — `RecipeCockpitRecordCreation` imports nothing and holds the rules: `isValidCreateCount` (an integer 1–200, nothing else), `findRequiredLookups` (not nillable, createable, not `defaultedOnCreate`, never `RecordTypeId`), `buildCreateReadiness` (an undefined org type, `isSandbox !== true`, no describe, an uncreateable object, a polymorphic required lookup, a parent with 0 or uncounted records — each a reason, never a default that lets Create through) and `assignLookupIds` (randomness handed in). Readiness also checks the fields of the block the insert would send (#210): `listCreateBlockFieldApiNames` reads them back from the same `extractObjectBlock` cut (Data-by-Org lists a whole tree through `listCreateBlockFieldApiNamesForObjects`, ONE scan per recipe, falling back to the per-object cut only where it would refuse — per-object calls were 25 s at 1,000 objects), `checkRecipeFields` matches them case-insensitively through a null-prototype map, and a field the describe lacks or will not let the user set is a reason — a lookup the describe knows never is, since the Create fills or removes it. Because one object can sit in several trees with different blocks, that check is per TREE AND OBJECT (`computeCreateReadinessByTarget`, posted as `createTargets` beside the object-wide readiness, which a row falls back to), costs no request beyond the describes the object guards already loaded, and a recipe it cannot read or cut is a reason too. `performCreate` re-checks with the fields of the block it just cut. The production guard is held THREE times on purpose: the router refuses a `createRecords` unless the selection's own Organization answer was a sandbox (so a forged message never connects), `performCreate` asks the Organization row AGAIN on the connection it will insert with, and the readiness built from that answer must have no reason. The panel posts org INDEX, tree key, object and count; the tree and object are matched against `creatableObjectKeys` (pending/active) and the recipe file is the host-only one ▶ Run Faker uses. The modal is HOST-side and lists what the host checked; Cancel returns before any parent Id is queried or file written, and the selection is compared again after it. The cut recipe is `extractObjectBlock` — lines copied from the tree's recipe, not rebuilt, its own `friends:` left out — run through the configured processor unchanged; every lookup is then replaced (required → a random Id from `queryRecordIds`, others removed), so a TODO or ancestor nickname never reaches the org. The insert is `insertRecordsWithoutRollback` (`allOrNone: false`, never deletes); its results file is what View errors opens, kept host-side per username, tree and object and posted with `dataOrgReadiness` so it survives the reload a Create ends with, which, like Run Faker's, happens however the Create ended once a data set folder exists, and opens the card the Create was clicked in on its Data-by-Org tab (`focusTree {treeKey, tab: 'dataByOrg'}`)
- **The Recipe Cockpit writes a recipe by patching LINES, never by round-tripping YAML** — both backends emit recipes as template strings, and the `### TODO` comments in them carry meaning (which record type to pick, which lookup needs a reference) that `js-yaml` drops on `dump`, so a load-and-dump is lossy by construction. `RecipeCockpitRecipeWriter` is pure and imports NOTHING (a test fails if it gains an import): text in, text plus an `edit` or a typed refusal out. It holds to the same layout contract `parseRecipeSource` reads — the reader IS its `scanRecipeObjects` — and every line outside the touched field's own lines is byte-identical afterwards, line ending included — new lines take the ending of the line they follow, and a missing final newline stays missing. The READER takes the first occurrence of an object or field, which is right for jumping to a line and wrong for changing one, so the WRITER refuses a duplicate object, field, `fields:` block or property rather than guessing which the reader meant. A friend under `friends:` (#46) is the same contract shifted: `scanRecipeObjects` keeps the open objects as a stack, one per level, the object at depth d has its `- object:` at column 4d and every other column (`getObjectLayout`) four spaces deeper per level, and a `- object:` line opens a friend ONLY one level down and only inside its parent's `friends:` block — anywhere else it is an unrecognized line, as it always was. A value handed to `insertField`/`replaceFieldValue` is written as for a top-level object and its continuation lines are moved to the friend's depth, so no caller has to know the depth. `commentOutField` is the removal because it is reversible: the lines sit at the FIELD column (four spaces at the top level) under a `### TODO -- RECIPE COCKPIT -- FIELD COMMENTED OUT -- <field> -- <n> lines` marker (deeper would read as the previous field's continuation), their encoding has one inverse, and `restoreCommentedOutField` gives the original back byte for byte. The COUNT is what bounds a restore — without it a reader's own comment directly below read as more of the field — and restore refuses unless those lines are still exactly what was written — which is why the reader treats a comment at field depth or shallower as ending the FIELD and not the BLOCK. The `yaml` package's comment-preserving `Document` API was the alternative; it is a new runtime dependency and re-flows `${{ }}` scalars, so it would still need every fidelity test. Values and names are validated so no argument can add a line the layout would read as another field or object — and that includes the line breaks the JS split does not see: PyYAML (snowfakery's reader) breaks at U+0085, U+2028 and U+2029, so a value carrying one is refused rather than split. Every call scans the whole file, so bulk edits need a one-scan batch entry point before a slice applies them. `insertFriend` (#197) is the one operation that ADDS an object: it copies the friend's own block from the occurrence above a self-lookup iteration (never its `friends:`), one level deeper, with a nickname no occurrence holds and every value that was the top occurrence's nickname re-pointed at the iteration's, and it reads its result back through `scanRecipeObjects` before answering. `listInsertableFriendObjectApiNames` is what the cockpit's **+** offers, so the panel and the writer share one answer — `parseRecipeSource` calls it for EVERY iteration at every load, so it takes the `buildScannedFriendIndex` built once per scan and must never walk the whole scan per call (that was 18 s at 11,000 objects); it also refuses a copy carrying a lone CR or U+0085/U+2028/U+2029, since text after one would keep its old column; the panel posts `addIterationFriend` with four NAMES, matched against `insertableFriendTargets` (pending/active, keyed by tree, object, nickname and friend, mapped to the host-only recipe file), and the host asks in a modal, writes and reloads focused on the card's Structure tab
- **A data set records its source by NAME, and the reader never trusts the names** — Run Faker by Recipe writes `BaseArtifactFiles/datasetSource.json` naming the recipe run folder, tree folder and recipe file, taken from the recipe's position under `GeneratedRecipes/` (`null` run and tree for a recipe directly under it). It is a file in the user's workspace, so `DatasetSourceService.readDatasetSource` type-checks every field (`unreadable` otherwise), refuses any name with a separator or `..`, and links only a name that matches a run and tree folder on disk (`unknown` otherwise). It never throws: a data set the reader cannot place is a status, not a failure of whatever lists it. A data set from before the file is linked only when its single recipe copy and single wrapper copy agree on a run that is still there — anything ambiguous is `unknown` rather than a guess. Its `origin` is `runFaker` or `createInOrg` (#180), and `orgUsername`, `createdObjectApiName` and `createdRecordIds` are present exactly when it is `createInOrg`. The data set folder takes the first free of `<name>`, `<name>-2`, … with `mkdirSync` as the existence check, and every reader of data set folder names must accept that suffix. The service imports only `fs` and `path`, so the cockpit and any non-vscode tooling can read it
- **A tree card's history is keyed by the tree's FOLDER NAME, and the panel posts only NAMES** — Previous Versions lists every run whose folder carries the tree's folder (`DatasetSourceService.findKnownRecipeRuns`), newest first by timestamp SUFFIX; Previous Fake Sets lists every data set `linked` to that folder, or `unknown` with a `treeFolderNameHint` ("version unknown"), and everything else is ONE unmatched count in a notice, never guessed onto a card. Versions and data sets are discovered when the model is built (directory listings and the small `datasetSource.json` files); a run's WRAPPER is read only when Previous Versions is first opened — one wrapper per event-loop turn, each posted as it is read, into a field-count cache keyed by path, size and mtime that OUTLIVES a model (the load seeds the current run's, so it is never parsed twice) — and a legacy data set's Collections API files only when the reader asks (a version expanded, or the row's `Show record counts`). A `focusTree` rides on the POSTED copy of a reload's model, never the stored one, or every reveal would replay it. Diff, Open, Insert, summaries and legacy counts each have their own pending/active allow-list (`IRecipeCockpitTreeHistoryAllowLists`, built from the rendered histories, promoted on `rendered`, emptied on `ready`, a new post and a failure to draw), and each posted name resolves through `IRecipeCockpitTreeHistoryTargets`, a host-only map built with the model — the posted model names no path. Every such path passes `isPathContainedInWorkspace` when the map is built AND, with an existence check, when it is used; a data set gone by then reloads the run with a `focusTree` that re-opens the reader's card and tab. `Insert…` executes `treecipe.insertDataSetBySelectedDirectory` with the folder: its handler takes an optional path, refuses one that is not an existing directory inside the workspace (the command is callable by id), and its registration RETURNS the promise. A version's field count is the WRAPPER's, so it leaves out the recipe-only rows the card header counts — compare like with like. **▶ Run Faker** follows the same shape: the panel posts the tree KEY, `runnableTreeKeys` (pending/active) gates it, and `runFakerRecipeFilePathsByTreeKey` (host-only, the current run's single contained `.yml`) resolves it. `treecipe.runFakerByRecipe` takes that path and RETURNS its promise; with a path its handler skips the picker but refuses a non-`.yml` file, one outside `GeneratedRecipes/` or the workspace, a missing file, and a recipe for the other backend (`VSCodeWorkspaceService.readRecipeFakerService`, held by a test to the picker's own walk). Then the cockpit reloads the run focused on Previous Fake Sets HOWEVER the command ended, because the panel disabled every Run Faker on the click and only the host's `runFakerState` (replayed on `ready` while in flight) enables them again
- **Node's internal rimraf binds `fs` functions the first time `rmSync`/`rm` runs** — so a `readdirSync` spy active at that moment breaks every recursive `rmSync` for the rest of the jest worker, beyond what `CoreModuleIsolation` can restore. `captureFunctionsOncePerWorker` calls `loadLazyFsInternals` before any test for that reason; do not remove it
- **The Recipe Cockpit draws every colour from ONE palette and reads none from the theme** — `RECIPE_COCKPIT_PALETTE` is written into the shell as `--sdt-*` properties on `:root`, and the only `--vscode-*` reads allowed are the three font variables; a test fails on any other. Every text/background pair the stylesheet draws is in the contrast test's pair list and held to WCAG 4.5:1, so a new pair (a new text token on a new background) goes into that list in the same change. One palette and no dark variant, on purpose: a theme-following cockpit rendered as a flat black page under dark themes. A tree card's HEADER is the toggle (#209): the `▸` carries no listener, so its click bubbles to the row like any other, and ▶ Run Faker sits in `.treeHeaderActions`, which stops the click on the GROUP — a browser can hand a click on a disabled button to its ancestors without running the button's listener. The panel harness bubbles events and skips a disabled element's own listeners to hold that worst case
- **`SfdxProjectService` is a leaf on purpose** — `fs` and `path` only, no `vscode` and no other service. `VSCodeWorkspaceService` needs the same workspace-containment logic the Apex-writing commands use, and importing `PicklistDependencyTestService` for it would close the cycle `VSCodeWorkspaceService → PicklistDependencyTestService → RecipeService → ErrorHandlingService → VSCodeWorkspaceService` and drag `@salesforce/core` into config initiation. `PicklistDependencyTestService` keeps its four helpers as delegations; `isPathContainedInWorkspace` passes its OWN realpath resolver down, so that service stays the single source of truth for how its paths resolve and the spies in its tests still intercept
- **Reading `sfdx-project.json` has two directions, and they are not interchangeable** — the commands that write Apex use `resolveDefaultPackageDirectoryPath`, which THROWS on a missing, unparseable or unusable project file because they cannot proceed without a package directory. Config initiation must proceed: a user who is not in a DX project still gets the full workspace walk, so it reads through `SfdxProjectService.resolvePackageDirectoryPaths`, which degrades every one of those cases to an empty list. The one case it reports is a file that IS there and cannot be parsed — an absence is a fact about the project, a parse failure is a typo the user wants told
- **The objects picker opens BEFORE its own scan, and the USER'S ANSWER ends the command** — `promptForObjectsPath` shows a `busy` quick pick and streams directories in as the walk finds them, because the notification whose button started the command is already gone (VS Code dismisses one the moment a button is clicked, and offers no way to keep it open or put a spinner in it). The selection is RACED against the scan and a response is itself a reason to stop walking: awaiting the walk and only then reading the selection puts the original stall back one layer down, and lets a later Cancel discard a choice the user already made. Item assignments are batched (200 items / 100ms) because `.items` is an ext-host round trip that re-sends the whole list, and the active item is restored across each flush or the scan drags the user's highlight to the top while they read. The cancellable `withProgress` is what makes the walk stoppable; `ProgressLocation.Window` cannot, so it is not used here either
- **The injectable realpath resolver on `isPathContainedInWorkspace` takes a REAL resolver, always** — it exists so a caller that owns its own `getRealDirectoryPath` stays the source of truth for how its paths resolve. An identity function passed here would defeat the symlink half of the containment check. The lexical half never passes through the resolver, so no injected resolver can make a `../` or absolute path pass — but it can hide a symlink escape
- **The `treecipeConfigurationPath` setting is a cache of a path, and a cache can be stale** — it holds an ABSOLUTE path saved the first time the config was found, so a moved or re-cloned project, or a `.vscode/settings.json` from another machine, leaves it naming a file that is not there (#171). `ConfigurationService.resolveTreecipeConfigurationFilePath` uses a stored path only when it is inside the workspace (`isPathContainedInWorkspace`, checked FIRST so an outside path is never read, with both drive letters lower-cased by `normalizeDriveLetterCase` because `uri.fsPath` gives `c:` and a hand-written setting `C:`) and is a file, and otherwise falls back to `<workspace>/treecipe/treecipe.config.json` — rewriting the setting and warning ONCE per value, and only when that file exists (a failed rewrite warns on its own, so rewriting per read repeated that warning per read). It reads the setting with `inspect()` (`getWorkspaceScopedExtensionConfigValue`) and never the User value, because `get()` merges User settings in and a User value applies to every window. A config missing everywhere throws `MissingTreecipeConfigurationError`, which keeps the prefix `ErrorHandlingService` keys on and carries the stale-setting notice separately. Workspace text shown in a notification goes through `RecipeYamlScalar.escapeForNotification`
- **Generate Treecipe reports through a vscode-free port, and a cancel is not an error** (#216) — the command runs inside one cancellable `ProgressLocation.Notification` and hands `DirectoryProcessor` an `IRecipeGenerationProgress` (`report`, `isCancellationRequested`). `processDirectory` checks for a cancel before each directory it enters, and `processAllObjectsAndRelationships` checks again after the walk and after the trees are built. The command checks after the global value sets load and once more before writing, and never after that, so a run folder is written whole or not at all. A cancel throws `RecipeGenerationCancelledError`, which the command answers with an information message and NEVER routes to `ErrorHandlingService`. It still returns normally, which is what lets the Recipe Cockpit's Regenerate reload. "N of M" counts the top-level directories of the configured objects path, so the total is known before the walk descends. A walk run without a port behaves exactly as before
- **Relationship grouping** — `RelationshipService` determines which objects belong in the same Treecipe file and in what insertion order
- **A faker-js tree nests its children under `friends:`; a snowfakery tree stays flat** (#46) — `DirectoryProcessor` turns nesting on from the faker service INSTANCE that writes the object recipes, not by reading the configuration again. Each object is still written once; it is nested under its CLOSEST parent that has a recipe (deepest level, ties by `<`), and only a parent at a strictly LOWER level qualifies, so the chosen parents are a forest whatever cycles the lookups contain. A lookup to ANY ancestor on the chain is written as that ancestor's nickname — only a line that is exactly `RelationshipService.referenceIdRequiredTodo` — and so is a lookup to a NON-ancestor parent that has a recipe in the same tree at a strictly LOWER level, because a lower level is inserted first (#189); `wireLookupsToParents` decides both. Every other generated lookup TODO in a nested tree — a parent with no recipe, a cycle (same or higher level, a self-lookup's top iteration included) — gets ` -- <Parent>` appended, so the TODO says what it needs. `FakerJSRecipeProcessor.resolveNonAncestorNicknameReferences` resolves the non-ancestor nicknames AFTER the whole recipe is generated, so document order does not matter: a field whose value is exactly an entry's YAML nickname, and that the ancestor map did not already resolve (`_ancestorResolvedFieldNames`, carried per friend), is pointed round-robin, in generation order, at that entry's records, never at itself. Insert resolves a nickname to the FIRST record holding it, and an entry with `count > 1` and no friends gives every record one nickname, so only for an entry a reference names those records are renamed `<nickname>_<n>`, skipping names already held — a data set nothing names is written exactly as before. Those records have no friends, which is what makes renaming them safe; a change that renames a record with friends breaks every child's ancestor reference. An object with a SELF-lookup gets ONE more friend, last in its `friends:` block: itself again, nicknamed `<Object>_child_NickName`, every self-lookup wired to the iteration above because it is passed as its own ancestor, and carrying no friends of its own, so nothing recurses (#188). That puts a parent and its child in one `collectionsApi-<Object>.json`, which is why `CollectionsApiService.partitionRecordsIntoInsertRounds` inserts a file in rounds: a record naming another record of the SAME file waits for the round that inserts it, and a file with no such reference is one round, the request it always was. The Recipe Cockpit tells two occurrences of one object apart by NICKNAME, never by api name: the scan records `nicknames` and `parentHeaderIndex`, `parseRecipeSource` keeps a later occurrence as an `iterations` entry on the first only when each carries a nickname no other occurrence does (else first-wins, as before), and every writer operation takes an optional `objectNickname`; without one, an object written twice is still refused. A tree where nothing nests goes through `buildCombinedTreeRecipe` unchanged, byte for byte. Two consumers make the wiring true at run time and both must stay: `FakerJSRecipeProcessor` hands each friend a `Map` of every ancestor's YAML nickname to the nickname of the record it is generated under (not only the direct parent's — with `count > 1` a grandchild's top-parent lookup would otherwise name no record), and `CollectionsApiService.updateLookupReferencesInCollectionApiJson` replaces a JSON string only when the WHOLE string is a nickname, because a friend's generated nickname CONTAINS its parent's (`Contact_Account_NickName`) and a substring replace rewrote the friend's own `referenceId`. The DirectoryProcessor suites load `objectInfoWrapper.RecipeFiles` — what is written — and `generatedRecipeYaml` holds every nested object to the flat recipe's fields apart from the wired lookups

## Implementation Checklist

When implementing a new feature or fixing a bug:

- [ ] Read the relevant service file(s) before making changes
- [ ] Add or update tests in the service's `tests/` folder
- [ ] If adding a new Salesforce field type handler, implement it in **both** `FakerJSRecipeFakerService` and `SnowfakeryRecipeFakerService`
- [ ] Add XML fixture files to `tests/mocks/` if the change depends on specific XML markup
- [ ] Run `npm run jest-test` — all tests pass, coverage does not regress
- [ ] Run `npm run compile` — zero TypeScript errors
- [ ] Run `npm run lint` — zero ESLint errors
- [ ] Update `CHANGELOG.md` with the change under an appropriate version heading

## Common Tasks

### Adding a New Salesforce Field Type Handler

1. Identify the Salesforce `<type>` value (e.g., `"Checkbox"`, `"Date"`)
2. Add a handler in `FakerJSRecipeFakerService.ts` that returns the appropriate faker-js expression
3. Add the equivalent handler in `SnowfakeryRecipeFakerService.ts`
4. Add tests for both in their respective `tests/` folders, with sample XML in `mocks/`

### Adding a New VS Code Command

1. Declare it in `package.json` under `contributes.commands`
2. Register it in `extension.ts`
3. Implement the handler in `ExtensionCommandService.ts`
4. Wrap in `ErrorHandlingService` for consistent error reporting

```bash
npx jest DirectoryProcessingService
npx jest FakerJSRecipeFakerService
npx jest --testPathPattern="RecipeFakerService"
```

