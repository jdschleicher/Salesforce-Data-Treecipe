# Claude Code Assistant Instructions - Salesforce Data Treecipe

## AI Context & Project Overview

You are assisting with **Salesforce Data Treecipe**, a **VS Code extension** (TypeScript) that auto-generates fake-data recipe YAML files from Salesforce object metadata (source format). It supports two faker backends: **faker-js** (built-in, no setup) and **snowfakery** (external Python CLI). The extension bridges Salesforce source-format XML metadata → YAML recipe files → Salesforce Collections API datasets.

## Key Project Files

- `src/extension.ts` - VS Code extension entry point; registers all commands
- `src/treecipe/src/` - All core service logic (one folder per service)
- `src/treecipe/src/RecipeFakerService.ts/` - **Directory** (not a file) containing `FakerJSRecipeFakerService/` and `SnowfakeryRecipeFakerService/` implementations
- `src/treecipe/src/FakerRecipeProcessor/` - Interface + FakerJS and Snowfakery recipe processor implementations
- `src/treecipe/src/DirectoryProcessingService/` - Parses Salesforce object metadata XML directories
- `src/treecipe/src/RelationshipService/` - Groups objects into Treecipe files by relationship hierarchy
- `src/treecipe/src/RecipeService/` - Orchestrates recipe YAML file creation
- `package.json` - Extension manifest; commands under `contributes.commands`, the Treecipe Activity Bar container and view under `viewsContainers`/`views`/`viewsWelcome`
- `jest.config.js` - Jest configuration (`ts-jest`, `jest-extended`)
- `CHANGELOG.md` - Feature history; read before starting work to understand recent changes

## Primary Objectives

1. **Follow existing service patterns** - Each service is a class in its own folder; tests live in a `tests/` subfolder alongside the service file
2. **Field-type-driven generation** - Recipe output is determined by Salesforce XML `<type>` tag; use `<precision>` and `<scale>` to constrain numeric/currency values
3. **Support both faker backends** - Every field-type handler must have equivalent implementations in both `FakerJSRecipeFakerService` and `SnowfakeryRecipeFakerService`
4. **Write tests first** - Every service has a `tests/` folder with Jest specs; add or update tests with every change

## CRITICAL RULES - NO EXCEPTIONS

### After Every Code Change

1. **Run tests** - `npm run jest-test` — ALL must pass
2. **Check coverage** - Coverage must not regress
3. **Compile** - `npm run compile` — zero TypeScript errors
4. **Lint** - `npm run lint` — zero ESLint errors
5. Check that existing functionality is not broken
6. Follow the established code patterns in the project

### Testing Requirements

- **Tests are mandatory** - Run `npm run jest-test` after EVERY code change
- **Update tests each change** - When modifying any service, add or update the corresponding test file in its `tests/` folder
- **Tests must pass before committing** - Never commit code with failing tests
- **Test coverage grows with features** - Every new feature, bug fix, or refactor must include relevant test updates
- **Mock fixtures** - Place sample Salesforce XML metadata in `tests/mocks/` inside the relevant service folder
- Use Jest `describe`/`it` or `describe`/`test` blocks; use `jest-extended` matchers where appropriate
- `restoreMocks: true` is set globally — do not manually restore mocks between tests
- **Never replace a Node core module function by assignment** (`fs.promises.readdir = jest.fn()`); always use `jest.spyOn`. `restoreMocks` restores only what `jest.spyOn` registered, and a core module is shared by every suite in a worker rather than rebuilt with the module registry, so an assignment leaks into whichever suite jest schedules next. `jestSetup/CoreModuleIsolation.ts` puts such a replacement back after every test — it is a net, not a licence. Its `afterEach` runs BEFORE a test file's own root-level `afterEach` (root-block hooks run in declaration order, and setup files are evaluated first), so a file-scope `afterEach` cannot assert on an `fs` spy

### Code Style Mandates

- **TypeScript strict** - No implicit `any`; always define types/interfaces
- **Class-based services** - Each service is a `class` with `static` methods; no standalone functions scattered outside a class
- **Interface-first for faker services** - Both faker backends implement `IRecipeFakerService` and `IFakerRecipeProcessor`
- **No hard-coded Salesforce field values** - All field type mappings must be driven by the XML `<type>` value
- **Naming conventions** - PascalCase for classes/interfaces, camelCase for methods/variables; service files match their class name
- **No comments for self-evident code** - Only add comments where the logic is non-obvious

## Architecture Patterns

### Extension Command Flow

```
User runs command (Cmd+Shift+P)
  → extension.ts registers command → ExtensionCommandService handler
    → ConfigurationService reads treecipe.config.json
      → DirectoryProcessingService walks salesforceObjectsPath
        → XmlFileProcessor parses each field's XML
          → ObjectInfoWrapper wraps parsed metadata
            → RecordTypeService / ValueSetService / RelationshipService enrich data
              → RecipeService orchestrates YAML generation
                → FakerJSRecipeFakerService OR SnowfakeryRecipeFakerService
                  → generates faker expression per field type
                → Writes YAML recipe file(s) to workspace
```

### Key Design Decisions

- **`RecipeFakerService.ts` is a directory** — it contains both faker implementations as subfolders; this naming is intentional and must not be changed
- **Apex written into a user's project is `SDT`-prefixed** — every class in `apexPicklistDependencyFramework/SDTPicklistDependencyFramework/` (the framework source shipped in the .vsix and scaffolded into the user's package directory), and every class the generator emits, starts with `SDT` so it cannot collide with the user's own Apex. Keep new Apex consistent with this
- **Every picklist value reaches a recipe through its backend's escaper or `buildDependentPicklistChoiceItem`, never raw** — values come from metadata a repository author controls, and there are six sinks per backend: the default and record-type expressions, a dependent picklist's `when:` and its choices, a record type's dependent choices, and the TODO naming a controlling value. The expression escaper is per LANGUAGE (`escapePicklistValueForJavaScriptString(value, quote)` for faker-js, `escapePicklistValueForJinjaStringLiteral` for snowfakery); the YAML half is shared in `RecipeYamlScalar`, because PyYAML ends a line at U+0085, U+2028 and U+2029 where js-yaml does not, and a value is only inert if NEITHER parser sees a break. A dependent choice is a YAML item rather than an expression, so it stays plain when safe (`isSafeAsPlainScalar`: no structure, no template delimiter, and nothing YAML would read as a boolean, null or number — `Yes`/`No` came back as `True`/`False`) and is quoted otherwise. In snowfakery an item carrying a template delimiter is also written as a Jinja literal, because snowfakery renders a string in whichever of its environments the string's delimiters select, quoted or not — and its DEFAULT mode (`snowfakery_version` 2) has TWO: `${{`/`${%`, and a legacy, unsandboxed `<<`/`<%` one. Missing the second is how `<< … >>` in a picklist value executed a shell command in review. `renderWithSnowfakeryJinja` copies that compiler selection; keep it a copy of snowfakery's `JinjaTemplateEvaluatorFactory`, not a guess at it. `FakerJSRecipeProcessor.parseWhenCondition` is the inverse of the faker-js `when:` escaping; change the two together. `buildRecipeWithEveryPicklistSink` and `DirectoryProcessor.hostilePicklistValues.test.ts` hold every sink to the same payload list, so a new sink that skips the escaper fails there
- **A metadata NAME reaches a recipe only if it IS a Salesforce api name** — field `<fullName>`, record type `<fullName>` and `<controllingField>` all come from workspace XML, and a line break in any of them used to start a recipe line of its author's choosing, whose `${{ … }}` faker-js evaluates with `new Function()` (#120). There is one guard per NAME, not per sink: `appendFieldRecipeToObjectRecipe` is the single place a field KEY is written (OOTB entries, field files, record type line, compound components) and drops the value with a refused key, because a value can embed the same name; `partitionRecordTypesByWritableDeveloperName` splits record types where they are LOADED, so the header and every record-type line in both backends only ever see valid names; `getDependentPicklistRecipeFakerValue` refuses a controlling field before either backend's `when:` is built. A refused name becomes one `### TODO -- … SKIPPED` comment, escaped through `RecipeYamlScalar.escapeForComment`. Rejected rather than quoted: a quoted key is valid YAML but names a field no org can have. A refused dependent picklist's value is that comment, so it loads as `null` — which is why `FakerJSRecipeProcessor` checks for a non-null OBJECT before `'if' in`. A new name that reaches a recipe, or a new sink for one of these three that bypasses its guard, re-opens the hole. OBJECT names are guarded at the one door into the map: `ObjectInfoWrapper.addKeyToObjectInfoMap` refuses anything that is not an api name, records it in `SkippedObjectApiNames` (absent when nothing was refused) and returns `false`, and `DirectoryProcessor` warns once after the walk (#164). That warning goes through `escapeForNotification`, which escapes `[`, `]`, `(` and `)` as well as line breaks: a VS Code notification renders `[label](command:…)` as a link that RUNS the command, so any workspace text shown in one needs the same treatment. A directory name and a lookup's `<referenceTo>` or relationship mapping both reach it, so a caller that adds an object any other way, or indexes the map with a name it did not get `true` for, re-opens the hole. The rule itself is `SalesforceApiName`, which imports NOTHING because `ObjectInfoWrapper`, `SOQLTemplateService` and `MermaidService` run without vscode; `SOQLTemplateService` leaves out every field, record type and `<referenceTo>` it refuses, and `MermaidService` every field, so both markdown files agree with the recipe. Error notifications get it CENTRALLY: `ErrorHandlingService.handleGenericError` escapes `error.message` and `handleMissingTreecipeConfigSetup` the stale-setting notice, because an error message can quote workspace text (a `js-yaml` parse error quotes the recipe line) and every `handleCapturedError` caller lands there (#186). The Report Issue URL keeps the RAW text, and `escapeForNotification` is idempotent on its own output, so an already-escaped notice is not doubled.
- **A map keyed by picklist VALUES has no prototype** — a value can be `constructor`, `toString` or `__proto__`, and a `{}` map reads the inherited member back (`push is not a function`, `not iterable`) or, on `__proto__`, replaces the prototype and loses the value. Build such a map with `Object.create(null)` and test membership with an own-key check, never `in` (#160). `DirectoryProcessor.prototypeNamedPicklistValues.test.ts` runs every one of those names through both backends and the spec generator
- **A SELECTED record type is narrowed in `RecipeService`, never in a backend** (#193) — `RecordTypeSelection` (object api name → developer names, in order) reaches generation as `generateRecipeFromConfigurationDetail`'s `{ recordTypeSelection }` option, type-checked by `RecordTypeSelection.fromUnknown` because the command is callable by id, then `DirectoryProcessor.processAllObjectsAndRelationships`. `resolveForObject` matches names against the WRITABLE map only (own keys), so a selected name reaches a recipe only if the metadata holds it under a valid api name; every other name is one `### TODO -- RECORD TYPE SELECTION IGNORED` line escaped through `escapeForComment`, written in the first block. For a selected record type `RecipeService` swaps each picklist's values for the record type's own section (a field it does not list keeps its values: a Checkbox controller is never listed), narrows a dependent picklist with `narrowControllingValueToPicklistOptions` (an unavailable controlling value's choice dropped, the dependent values intersected, an emptied choice dropped, nothing left → a `### TODO` value that loads as null), and hands the backend an EMPTY record type map. So neither backend has a selected-record-type path to keep in sync, every value still goes through its escaper, and no selection is byte-identical output. Adding a record-type sink to a backend means narrowing it here too. `buildRecipeWithEveryPicklistSinkForSelectedRecordType` and the hostile pipeline suite hold the selected path to the same payloads
- **Several selected record types are several BLOCKS of one object, and only the first carries friends** (#194) — `RecordTypeSelection.buildRecordTypeBlocks` decides them: none or one selected is ONE block under `<Object>_NickName` (so the output is #193's, byte for byte), several are one block each, in selection order, nicknamed `<Object>_<DeveloperName>_NickName` (a reserved nickname, the self-lookup iteration's, takes `_RecordType_NickName`). `DirectoryProcessor` writes the first block into `FullRecipe` and the rest into `ObjectInfo.AdditionalRecordTypeRecipes` (set only when there are several), reading the fields again per block (`buildAdditionalRecordTypeRecipes`) so `Fields` and every relationship stay the first block's. `RelationshipService` writes the later blocks right after the first: flat, or nested at the same depth with the same ancestors. Friends, and the self-lookup iteration, go under the FIRST block only (a decision on #194: every block would multiply the children's records), and `readNickname` of `FullRecipe` is what every wired lookup and #189 lower-level wiring names. A lookup still the REFERENCE ID REQUIRED TODO to a parent with several blocks gets a `### TODO -- RECORD TYPE BLOCKS --` comment line under it (`annotateLookupsToRecordTypeBlocks`), never an edit of the lookup line, which #151's wiring matches exactly; a self-lookup never lists its own block. The Recipe Cockpit reads each later block as an occurrence told apart by nickname. A child's blocks are SIBLING friends of one object type, which `FakerJSRecipeProcessor` names `<YAML nickname>_<parent>` instead of `<Object>_<parent>` (only when a sibling shares the object type), because records sharing a nickname share a `referenceId` and the insert resolves a nickname to the first record holding it
- **Record types are CHOSEN in the Recipe Cockpit's Record types section, never prompted for by Generate Treecipe** (#195, a decision on the issue: a cockpit mode, so behind `recipeCockpitEnabled`, and no quick pick) — Generate Treecipe from the palette still asks nothing and writes defaults. `normalizeObjectsWrapper` sets `recordTypes` on an object only when `readRecordTypeOptions` finds two or more developer names that ARE api names (generation refuses any other), each with `isActive` and its `impacts` (picklist/multiselect/dependent field and a value COUNT, never the values). `applyGeneratedRecordTypes` reads what the run writes from every block's `RecordTypeId: Obj.Dev` line in the recipe files (`scanRecipeObjects`, block order, an iteration counted once) and sets `generatedRecordTypeDeveloperNames`, falling back to the first active record type; `isRecordTypeSelectionApplied` is set when no block of the object carries `RECIPE_COCKPIT_RECORD_TYPE_OPTIONS_MARKER` under its `RecordTypeId` — a test feeds it `RecipeService`'s own headers so a format change fails there. Since #321 it is a SECTION of the Treecipe tab, not a tab, and since #490 it is opened by **Manage record types**, a `secondary` button (`recordTypesSectionToggle`, `aria-expanded`/`aria-controls`/`aria-describedby` the summary beside it) in the `treecipeFilterTile` under the Treecipe search box, which also holds the **Click to show record type impacted fields only** and **Click to show fields with open TODOs** checks, one `treecipeFilterRow` each. The body (`buildRecordTypesSection`, `recordTypesSectionBody`, `role="region"`) sits under the tile and above the first object, collapsed by default; the summary says how many objects it lists and whether the choice is `changed`, `generated from a choice` or `generated by default`, and its rows are built on first expand (`buildRecordTypesRows`). Every card draws the button (#338); a card that lists no such object draws it DISABLED (`appendUnavailableRecordTypesButton`: native `disabled`, no `aria-expanded`/`aria-controls`, `RECIPE_COCKPIT_RECORD_TYPES_UNAVAILABLE_SUMMARY` beside it and as its title, no body, no listener, `treeState.recordTypesSection` unset so every open path stops at its guard). It has no search box of its own: the Treecipe search also narrows its rows (`applyRecordTypesFilter`, called from `applyStructureFilter`) and the summary counts the matches. The choice is the PANEL's, per object and shared by every card (`recordTypeChoices`, no prototype), starts from what is generated, keeps at least one ticked, and is ordered by ticking. **Regenerate with these record types** posts `regenerateWithRecordTypes {treeKey, recordTypeSelection}` with every object changed or already `isRecordTypeSelectionApplied` (so one regenerate does not reset another object's choice) and nothing for an object at its default; **Use defaults** posts `{}`. `readPostedRecordTypeSelection` matches every pair against `selectableRecordTypeKeys` (`"<object>\n<developerName>"`) and the card against `recordTypeTreeKeys` (both in `IRecipeCockpitTreeHistoryAllowLists`, pending/active) and refuses the WHOLE request on any name it did not offer. The executor is `generateTreecipeAndReload` with `{ ...RECIPE_COCKPIT_GENERATE_TREECIPE_OPTIONS, recordTypeSelection }` and a `focusTree` of `{ tab: 'treecipe', recordTypes: {} }`, which opens the section, sharing `isGenerateTreecipeInFlight` and reloading even when generation fails. It is refused while `insertStateMessage` is set (a reload clears the org selection a confirmed insert re-checks), and every refusal answers `recordTypeRegenerateState {isRunning: false}`, since the panel disabled the section on the click. The record types each block writes are collected in `parseRecipeSource`'s own scan (`collectRecordTypeBlocks`), never a second one. An expanded section is the place's optional `isRecordTypesExpanded`, so the place version did not change; `recordTypes` is in `RECIPE_COCKPIT_REMOVED_TREE_TABS`, and a place saved on that tab (by `normalizePanelPlace` and the panel's `upgradePlace`) opens on Treecipe with the section expanded and its search dropped. The same impacts drive the Treecipe tab's per-card **Record type fields only** check and each restricted row's chip (#320): `indexRecordTypeFields` reads them IN THE PANEL once per model (no prototype; a non-object impact, a field the object does not list and any `__proto__` name are skipped), the check narrows `applyStructureFilter` together with the search, never hides an object ("no record type fields"), is disabled with `RECIPE_COCKPIT_NO_RECORD_TYPE_FIELDS_NOTE` on a card with no object of two or more record types, and is the place's optional `isRecordTypeFieldsOnly`; the host posts nothing new for it
- **A record type selection is SAVED only from the Record types section, and a saved one is DROPPED, never partly applied, when it goes stale** (#196) — **Remember this selection** (unticked by default and with every model) makes `regenerateWithRecordTypes` carry `isRemembered: true`, and the host writes `recordTypeSelections` plus `recordTypesWhenSelectionSaved` (every record type each object had in the model on screen, host-derived, never posted) through `ConfigurationService.saveRecordTypeSelections` before regenerating; an empty selection (Use defaults) removes both keys, and a failed save warns and still regenerates. Generate Treecipe reads it (`readSavedRecordTypeSelection`) only when its options carry NO `recordTypeSelection` key (`hasRecordTypeSelectionOption`), so the section's explicit choice, and Use defaults' `{}`, always win. `SavedRecordTypeSelection` overrides `RecordTypeSelection.resolve` (the instance method `resolveForObject` delegates to), so the check rides the walk that already loads record types: an entry naming a record type the object's WRITABLE map lacks is dropped whole (default block, no IGNORED TODO), and the walk records missing objects and record types added since. One warning per distinct text per session (`showRecordTypeSelectionWarningOnce`), every name escaped, with **Change record types**, which runs `treecipe.openRecipeCockpit` `{ focusRecordTypes: true, objectApiName? }`. `readRecordTypesFocusRequest` keeps only that shape and an api name; the open loads the NEWEST run and `resolveRecordTypesFocus` picks the first card listing the object, with `focusTree.recordTypes.objectApiName` set, and the panel opens the section and scrolls that object's row into view (#321). A focus that scrolled is not scrolled back by `restoreScroll`, and a restored Treecipe search hiding the row is cleared first. The focus rides on every replay as `openFocusTree` until `rendered`, since an open posts before the document's `ready`
- **Generate Treecipe applies the constraints validation rules imply, and reports every rule it does not** (#324) — `DirectoryProcessor.readValidationRuleAnalyses` reads `<object>/validationRules/` from the object directory's OWN listing (no second walk), files sorted with `<`, only `<active>true</active>`; a file that does not parse or read is a rule not applied, never a failure. `ValidationRuleAnalyzerService` recognizes ONLY #41's single-field shapes (a formula is TRUE when invalid, so each is read inverted) and refuses everything else whole; numbers and dates are parsed and written back from what was parsed, and a field reference must pass `SalesforceApiName`. Rules reach a field through `buildFieldInfoByXMLContent` (keyed by lower-cased field name, as a formula is case-insensitive) and `RecipeService.applyValidationRules`, which groups them: bounds of the field's kind are intersected and resolved by `RecipeFieldConstraint` (#323's rule, so an empty intersection applies none, each saying why), an exclusive numeric bound moves one step of the SCALE inward in BigInt units (`roundNumberBoundIntoScale`), date rules apply to a Date field only, `ISPICKVAL` rebuilds the picklist through the backend's own builder with the values dropped (dependent choices, a selected record type and each record type variant included, on a COPY of the wrappers), a regex replaces the generator. The expression is the backend's `buildConstrainedExpression` or `buildRegexExpression` (snowfakery: `undefined`, so a regex rule is not applied there), held to `RecipeCockpitRecipeWriter.checkConstrainedExpression`, written double-quoted with one `### Driven by ValidationRule` line under it; every rule not applied is a `### TODO -- VALIDATION RULE NOT APPLIED` line at the end of the object's first block, names and reasons through `escapeForComment`. A regex is translated into atoms (literal, class, `.`, `\d`, `\w`, `\s`, quantifier) because Salesforce's REGEX matches the whole value; faker-js's `fromRegExp` gets only a class of `[A-Za-z0-9_]` because it skips most punctuation inside a class, so other sets go through `faker.string.fromCharacters` and literals through the picklist escaper. `FieldInfo.validationRuleConstraints` and `unconstrainedRecipeValue`, and `ObjectInfo.ValidationRulesNotApplied`, are set ONLY when there is a rule, so a workspace without `validationRules/` writes byte-identical output. The faker-js processor evaluates fields in order, so a dependent picklist still has to follow its controller
- **Both faker backends must stay in sync** — whenever a new field type handler is added to `FakerJSRecipeFakerService`, add the equivalent to `SnowfakeryRecipeFakerService`
- **Numeric/currency precision** — `<precision>` (total digits) and `<scale>` (decimal places) from XML drive `max` and `dec` parameters; `left_digits = precision - scale`
- **Picklist handling** — special characters (`&`, `'`, etc.) in picklist values must be escaped before embedding in faker expressions
- **A record type's picklist variant is a COMMENTED line** — a picklist or multi-select picklist with record-type values is written as its default expression, then per record type a `### TODO` and `# ${{ … }}`. A bare expression indented under a field's value is not YAML, and Run Faker by Recipe loads the WHOLE file, so one such line failed every object in the recipe in both backends (#153). `DirectoryProcessor.generatedRecipeYaml.test.ts` loads every file the real pipeline writes, with each backend, so anything else generation emits is held to the same bar. `RecordTypeId` follows the same rule: its value is ONE developer name, the first ACTIVE record type (the first if none is), and each other is a `# Obj.DeveloperName` line under its TODO — a bare name on the next line folds into the value, and the insert's Id swap then sends several Ids in one field (#157). One record type gets no TODO. "First" is a fixed order: `getRecordTypeToApiFieldToRecordTypeWrapper` sorts by developer name with `<`, never `localeCompare`, ONCE where record types are loaded, because `readDirectory` lists in the file system's order and that decided the inserted record type and every record-type section in both backends (#166). A consumer that re-sorts, or a second loader that skips the sort, makes a recipe depend on the machine again
- **The generated Apex test suite is the published handle, and regeneration MERGES it** — `SDTPicklistDependencyTests.testSuite-meta.xml` is what `--suite-names`, Setup and `Run Picklist Dependency Check` all address, so nothing downstream depends on the generated class name. Unlike the `.cls` files it is NOT owned outright: a suite is a grouping a team curates, so generation unions its member in and removes nothing, and a file it cannot parse as an `ApexTestSuite` is left exactly as it is with a warning. The suite lives in a `testSuites` sibling of the classes directory — one derivation, in `getTestSuitesDirectoryPath`, so the two cannot drift off `main/default` separately. Its file name ends in `-meta.xml` without being a sidecar, which is why report filtering keys on `.cls-meta.xml`
- **The deployed-check asks about suite MEMBERSHIP, never suite existence** — a suite whose member class was deleted still exists, and `--suite-names` against it runs zero tests and reports success. One Tooling API query over `TestSuiteMembership` answers both halves; anything cheaper is a green check that verified nothing. It is asked on a `SalesforceOrgService.getConnection` connection's `tooling.query` (#497), not `sf data query`, and a failed connection, a rejected query or an answer with no records list reads as "not deployed"
- **The check RUNS the suite through the Tooling API, and a cancel ABORTS it in the org** (#503) — `runPicklistDependencyTests` starts the run with `connection.tooling.runTestsAsynchronous({ suiteNames })` (never `classNames` or `tests`), holds the answered job id to the Salesforce Id pattern before quoting it, polls `AsyncApexJob` every `apexTestRunPollIntervalMilliseconds` until `Completed`, `Failed` or `Aborted`, and reads the outcome from `ApexTestResult` (every page) through `buildCheckOutcomeByTestResults`, which type-checks each row; `results.json` and `report.md` are built from that outcome as before. The wait is `apexTestRunWaitMilliseconds`, 10 minutes as `--wait 10` was, and a test pins it; a run still going then is LEFT RUNNING and named in the error, as the CLI left it. A cancel sets every `ApexTestQueueItem` of the run still `Holding`/`Queued`/`Preparing`/`Processing` to `Aborted` (the CLI's and Setup's abort), bounded by `apexTestRunAbortTimeoutMilliseconds`, and ends in `PicklistDependencyTestRunCancelledError`, whose message says whether the abort landed, which the command shows as information, never an error. A start request in flight when the cancel arrives is waited for, so a run the org started is still aborted
- **Org work goes through a `@salesforce/core` connection, and the `sf` CLI only where epic #496 has not replaced it yet** — open the org with `SalesforceOrgService.getConnection` (by username where the code has one) and use the `Connection` it returns (`query`, `tooling`, `metadata`, `sobject`). Never `import` `jsforce` itself: it is only a devDependency, and `.github/workflowScripts/checkPackagedPaths.js` fails a build whose shipped code requires a package `dependencies` does not declare; the connection IS the jsforce API that ships. `PicklistDependencyCheckService/tests/SalesforceCliCallSites.test.ts` lists every remaining `runSalesforceCli`/`runCancellableCli` call by file and method, the files that import `child_process`, and fails on a direct `jsforce` import: a new `sf` call needs a reason in its issue and its entry added there in the same change, and a #496 slice that removes one deletes its entry. The Troubleshooting deploys keep their `sf project deploy start` call site as the `cli` choice of `metadataDeployMethod` (#505); the `jsforce` choice deploys on the connection. A connection reads the access token into the extension host, so it is never written, logged, posted to a webview or quoted in a notification
- **The transpose is the writeback's whole reason to exist** — a validator failure is indexed by *controlling* value (`cle @ missing [plant]`) while `valueSettings` is indexed by *dependent* value (`plant ← cle`), so acting on a failure by hand means editing a block the message never names. `PicklistDependencyMetadataWriterService` owns that direction; keep it one function with one direction
- **Anything spanning a run is keyed by object AND field** — a run reconciles every per-object spec class at once, and field api names repeat across objects (`Status__c` on Account and on Case). `PicklistDependencyMetadataWriterService.buildFieldKey` is the one place that shape is defined; use it for every path map, dependency-graph key and report line rather than the bare field api name
- **Writeback merges intent, it does not substitute for it** — a spec asserts what a controlling value must and must not unlock; anything it names neither way it makes no claim about. Only `expectNone` and `expectExactly` are exhaustive and may remove. Reading silence as deletion would let a one-line spec strip a file
- **The spec manifest is the single source for the Explorer** — `Generate Picklist Dependency Tests` emits the Apex classes and `treecipe/PicklistDependencySpecs/manifest.json` from one in-memory model in one run, and the Explorer renders the manifest rather than re-walking the source XML. Anything that changes what the generator emits must flow through the manifest too, or the panel and the Apex become two derivations again. The manifest never goes in a package directory — a stray `.json` there breaks `sf project deploy`
- **The manifest records the information content of the specs, not their cross product** — what a controlling value must NOT unlock is the complement of what it unlocks within the field's declared values, so recording it per expectation grew `manifest.json` with *combinations x declared values* (315.7 MB, a 1.4 s parse, ~59% of an Explorer open). A field entry carries `declaredValues` ONCE and an expectation carries `forbiddenValuesAreDeclaredComplement`; `buildSpecDetailsByManifest` reconstructs the array on read so every consumer — the Explorer's rows, and `PicklistDependencyMetadataWriterService`, whose transpose REMOVES pairs by that list — is unchanged. The marker is DERIVED AND COMPARED before it is recorded, never assumed: a forbidden set that is not the complement is written out literally, which is what makes the round trip a property rather than a coincidence of the two current generators. Three states stay distinct because the panel renders them differently — the marker, a written-out list (`expectNone` and `expectUnavailable` assert an EMPTY set against a non-empty universe), and neither, which asserts only the positive half. The universe is the one the spec was drawn against, so a record-type-scoped field records what the RECORD TYPE assigns; and it must be COMPLETE, per the complement rule above. Order it once per FIELD (`buildOrderedDeclaredValues`) rather than inside each complement — that was measured at 594 ms against 59 ms and would have handed back most of the parse saving

Each Previously Used Data Sets row draws ☆ and ✎, which post only `{datasetFolderName}` (`toggleFavoriteDataset`, `renameDataset`), matched against `nameableDatasetFolderNames` inside `IRecipeCockpitTreeHistoryAllowLists`, added by `addDatasetToAllowLists` so a row added in place (#226) joins it only on `partialRendered`. The host asks in its own `showInputBox` (folder name through `escapeForNotification`) and checks with `validateDatasetName` while typed and again when it closes: one line, at most 80, unique trimmed and case-insensitive against other folders' stored names and every other row's folder name and name on screen. `applyDatasetPreferences` sets `customName`/`isFavorite` on every card's rows at post time (and `postAddedDataset` on the added one); a change updates the stored model and posts `datasetPreferences {renderSequence, datasetFolderName, customName?, isFavorite}`, which the panel draws on every card's row in place. The data sets tab's **Favorites only** is panel-only, per card, combined with the search, and saved in the tree place as optional `isDatasetFavoritesOnly`, so the place version did not change. The folder on disk is never renamed
- **`SfdxProjectService` is a leaf on purpose** — `fs` and `path` only, no `vscode` and no other service. `VSCodeWorkspaceService` needs the same workspace-containment logic the Apex-writing commands use, and importing `PicklistDependencyTestService` for it would close the cycle `VSCodeWorkspaceService → PicklistDependencyTestService → RecipeService → ErrorHandlingService → VSCodeWorkspaceService` and drag `@salesforce/core` into config initiation. `PicklistDependencyTestService` keeps its four helpers as delegations; `isPathContainedInWorkspace` passes its OWN realpath resolver down, so that service stays the single source of truth for how its paths resolve and the spies in its tests still intercept
- **Reading `sfdx-project.json` has two directions, and they are not interchangeable** — the commands that write Apex use `resolveDefaultPackageDirectoryPath`, which THROWS on a missing, unparseable or unusable project file because they cannot proceed without a package directory. Config initiation must proceed: a user who is not in a DX project still gets the full workspace walk, so it reads through `SfdxProjectService.resolvePackageDirectoryPaths`, which degrades every one of those cases to an empty list. The one case it reports is a file that IS there and cannot be parsed — an absence is a fact about the project, a parse failure is a typo the user wants told
- **The objects picker opens BEFORE its own scan, and the USER'S ANSWER ends the command** — `promptForObjectsPath` shows a `busy` quick pick and streams directories in as the walk finds them, because the notification whose button started the command is already gone (VS Code dismisses one the moment a button is clicked, and offers no way to keep it open or put a spinner in it). The selection is RACED against the scan and a response is itself a reason to stop walking: awaiting the walk and only then reading the selection puts the original stall back one layer down, and lets a later Cancel discard a choice the user already made. Item assignments are batched (200 items / 100ms) because `.items` is an ext-host round trip that re-sends the whole list, and the active item is restored across each flush or the scan drags the user's highlight to the top while they read. The cancellable `withProgress` is what makes the walk stoppable; `ProgressLocation.Window` cannot, so it is not used here either
- **`isPathContainedInWorkspace` checks the LEXICAL half first and realpaths nothing it refuses** (#456) — on Windows a realpath of a UNC path a workspace setting names (`\\host\share`) can contact that host, and the side bar runs the check at activation with no command run. A test holds that neither the default nor an injected resolver is called for a refused path
- **The injectable realpath resolver on `isPathContainedInWorkspace` takes a REAL resolver, always** — it exists so a caller that owns its own `getRealDirectoryPath` stays the source of truth for how its paths resolve. An identity function passed here would defeat the symlink half of the containment check. The lexical half never passes through the resolver, so no injected resolver can make a `../` or absolute path pass — but it can hide a symlink escape
- **The `treecipeConfigurationPath` setting is a cache of a path, and a cache can be stale** — it holds an ABSOLUTE path saved the first time the config was found, so a moved or re-cloned project, or a `.vscode/settings.json` from another machine, leaves it naming a file that is not there (#171). `ConfigurationService.resolveTreecipeConfigurationFilePath` uses a stored path only when it is inside the workspace (`isPathContainedInWorkspace`, checked FIRST so an outside path is never read, with both drive letters lower-cased by `normalizeDriveLetterCase` because `uri.fsPath` gives `c:` and a hand-written setting `C:`) and is a file, and otherwise falls back to `<workspace>/treecipe/treecipe.config.json` — rewriting the setting and warning ONCE per value, and only when that file exists (a failed rewrite warns on its own, so rewriting per read repeated that warning per read). It reads the setting with `inspect()` (`getWorkspaceScopedExtensionConfigValue`) and never the User value, because `get()` merges User settings in and a User value applies to every window. A config missing everywhere throws `MissingTreecipeConfigurationError`, which keeps the prefix `ErrorHandlingService` keys on and carries the stale-setting notice separately. Workspace text shown in a notification goes through `RecipeYamlScalar.escapeForNotification`
- **`salesforceObjectsPath` is resolved in ONE place and held to the workspace** (#117) — it comes from `treecipe.config.json`, which arrives with a cloned repository. Every command that walks the objects directory gets it from `ConfigurationService.resolveObjectsDirectoryPath(workspaceRoot)`: backslashes normalized, `path.resolve` against the workspace, then `SfdxProjectService.isPathContainedInWorkspace` (lexical and realpath). An absolute path is refused even inside the workspace, since the config writer only writes relative ones. A refusal throws a message naming the configured value BEFORE any directory is read. Never rebuild the path by string concatenation or `split("./")`. The `globalValueSets/` folder beside it comes from `resolveSalesforceMetadataParentPath` (`path.dirname`, the workspace root when the parent would be outside it) — the path is native, so a `/` split finds no parent on Windows
- **Generate Treecipe reports through a vscode-free port, and a cancel is not an error** (#216) — the command runs inside one cancellable `ProgressLocation.Notification` and hands `DirectoryProcessor` an `IRecipeGenerationProgress` (`report`, `isCancellationRequested`). `processDirectory` checks for a cancel before each directory it enters, and `processAllObjectsAndRelationships` checks again after the walk and after the trees are built. The command checks after the global value sets load and once more before writing, and never after that, so a run folder is written whole or not at all. A cancel throws `RecipeGenerationCancelledError`, which the command answers with an information message and NEVER routes to `ErrorHandlingService`. It still returns normally, which is what lets the Recipe Cockpit's Generate Treecipe button reload. "N of M" counts the top-level directories of the configured objects path, so the total is known before the walk descends. A walk run without a port behaves exactly as before
- **Relationship grouping** — `RelationshipService` determines which objects belong in the same Treecipe file and in what insertion order
- **A standard field with no `<referenceTo>` takes its parent from ONE static map, and only then** (#400) — `StandardFieldParentReferenceMap` (imports nothing, no prototype, own-key check) names the parent of `Account.ParentId`, `Contact.ReportsToId`, `Case.ContactId` and the rest by `Object.Field`. `DirectoryProcessor.applyStandardFieldParentReference` reads it for a Lookup, MasterDetail or Hierarchy field only when the XML has no `<referenceTo>` AND no custom relationship mapping names the field, so both still win (a mapped HIERARCHY field takes the mapping's parent as its `referenceTo`, because a Hierarchy's recipe value is decided by `referenceTo` alone); the answer is held to `SalesforceApiName` and set as the field's `referenceTo`, so it reaches the object map through `addKeyToObjectInfoMap` like any `<referenceTo>`. `RecipeService` writes a Hierarchy field WITH a parent as its backend's `lookup` value and one without as before ("FieldType Not Handled"), so an unmapped Hierarchy (`User.ManagerId`) is unchanged. The lookup type lists read `'Hierarchy'` (they read `'Hiearchy'` before #400, so no Hierarchy field ever reached a relationship). Never add a polymorphic field (`WhoId`, `WhatId`, `OwnerId`): one parent cannot be named. A new entry is a decision pinned in `StandardFieldParentReferenceMap.test.ts`
- **A faker-js tree nests its children under `friends:`; a snowfakery tree stays flat** (#46) — `DirectoryProcessor` turns nesting on from the faker service INSTANCE that writes the object recipes, not by reading the configuration again. Each object is still written once; it is nested under its CLOSEST parent that has a recipe (deepest level, ties by `<`), and only a parent at a strictly LOWER level qualifies, so the chosen parents are a forest whatever cycles the lookups contain. A lookup to ANY ancestor on the chain is written as that ancestor's nickname — only a line that is exactly `RelationshipService.referenceIdRequiredTodo` — and so is a lookup to a NON-ancestor parent that has a recipe in the same tree at a strictly LOWER level, because a lower level is inserted first (#189); `wireLookupsToParents` decides both. Every other generated lookup TODO in a nested tree — a parent with no recipe, a cycle (same or higher level, a self-lookup's top iteration included) — gets ` -- <Parent>` appended, so the TODO says what it needs. `FakerJSRecipeProcessor.resolveNonAncestorNicknameReferences` resolves the non-ancestor nicknames AFTER the whole recipe is generated, so document order does not matter: a field whose value is exactly an entry's YAML nickname, and that the ancestor map did not already resolve (`_ancestorResolvedFieldNames`, carried per friend), is pointed round-robin, in generation order, at that entry's records, never at itself. Insert resolves a nickname to the FIRST record holding it, and an entry with `count > 1` and no friends gives every record one nickname, so only for an entry a reference names those records are renamed `<nickname>_<n>`, skipping names already held — a data set nothing names is written exactly as before. Those records have no friends, which is what makes renaming them safe; a change that renames a record with friends breaks every child's ancestor reference. An object with a SELF-lookup gets ONE more friend, last in its `friends:` block: itself again, nicknamed `<Object>_child_NickName`, every self-lookup wired to the iteration above because it is passed as its own ancestor, and carrying no friends of its own, so nothing recurses (#188). That puts a parent and its child in one `collectionsApi-<Object>.json`, which is why `CollectionsApiService.partitionRecordsIntoInsertRounds` inserts a file in rounds: a record naming another record of the SAME file waits for the round that inserts it, and a file with no such reference is one round, the request it always was. The Recipe Cockpit tells two occurrences of one object apart by NICKNAME, never by api name: the scan records `nicknames` and `parentHeaderIndex`, `parseRecipeSource` keeps a later occurrence as an `iterations` entry on the first only when each carries a nickname no other occurrence does (else first-wins, as before), and every writer operation takes an optional `objectNickname`; without one, an object written twice is still refused. A tree where nothing nests goes through `buildCombinedTreeRecipe` unchanged, byte for byte. Two consumers make the wiring true at run time and both must stay: `FakerJSRecipeProcessor` hands each friend a `Map` of every ancestor's YAML nickname to the nickname of the record it is generated under (not only the direct parent's — with `count > 1` a grandchild's top-parent lookup would otherwise name no record), and `CollectionsApiService.updateLookupReferencesInCollectionApiJson` replaces a JSON string only when the WHOLE string is a nickname, because a friend's generated nickname CONTAINS its parent's (`Contact_Account_NickName`) and a substring replace rewrote the friend's own `referenceId`. The DirectoryProcessor suites load `objectInfoWrapper.RecipeFiles` — what is written — and `generatedRecipeYaml` holds every nested object to the flat recipe's fields apart from the wired lookups

## Implementation Checklist

When implementing a new feature or fixing a bug:

- [ ] Read the relevant service file(s) before making changes
- [ ] Add or update tests in the service's `tests/` folder
- [ ] If adding a new Salesforce field type handler, implement it in **both** `FakerJSRecipeFakerService` and `SnowfakeryRecipeFakerService`
- [ ] Add XML fixture files to `tests/mocks/` if the change depends on specific XML markup
- [ ] Run `npm run jest-test` — all tests pass, coverage does not regress
- [ ] Run `npm run compile` — zero TypeScript errors
- [ ] Run `npm run lint` — zero ESLint errors
- [ ] Update `CHANGELOG.md` with the change under an appropriate version heading

## Common Tasks

### Adding a New Salesforce Field Type Handler

1. Identify the Salesforce `<type>` value (e.g., `"Checkbox"`, `"Date"`)
2. Add a handler in `FakerJSRecipeFakerService.ts` that returns the appropriate faker-js expression
3. Add the equivalent handler in `SnowfakeryRecipeFakerService.ts`
4. Add tests for both in their respective `tests/` folders, with sample XML in `mocks/`

### Adding a New VS Code Command

1. Declare it in `package.json` under `contributes.commands`
2. Register it in `extension.ts`
3. Implement the handler in `ExtensionCommandService.ts`
4. Wrap in `ErrorHandlingService` for consistent error reporting

### Running Tests for a Specific Service

```bash
npx jest DirectoryProcessingService
npx jest FakerJSRecipeFakerService
npx jest --testPathPattern="RecipeFakerService"
```

```bash
# Read CHANGELOG.md top section, or:

```

## Remember

- **Both faker backends** - New field type handlers must be implemented in both FakerJS and Snowfakery services
- **Tests first** - Add/update tests in the service's `tests/` folder before or alongside code changes
- **No comments for obvious code** - Only comment where logic is genuinely non-obvious
- **`RecipeFakerService.ts` is a directory** - Do not confuse it with the `.ts` file of the same name in the parent folder
- **Precision/scale math** - `left_digits = precision - scale`; `max = 10^left_digits - 1`; `dec = scale`
- **Special characters in picklists** - Always escape before embedding in faker expression strings
