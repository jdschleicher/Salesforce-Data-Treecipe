# Salesforce org service — design notes

Design notes moved out of CLAUDE.md (#563). Read this before changing the service; CLAUDE.md keeps only the rules every change must follow. History is in CHANGELOG.md.

- **Every org picker lists only the authorizations that ANSWER A PING, checked in process, and fails closed** (#201, #502) — the Treecipe tab's picker, Insert Data Set by Directory, Run Picklist Dependency Check and the Dev Hub picker all read `SalesforceOrgService.listConnectedOrgAuthorizations()`, which runs NO process since #502 (`sf org list --json --verbose` and its parser are gone, and so is its entry in `SalesforceCliCallSites.test.ts`). `runOrgConnectionCheck` reads `AuthInfo.listAllAuthorizations()` (`readFreshAuthorizations`, `StateAggregator.clearInstance()` first, #286; a read that throws is `OrgConnectionStatusUnavailableError`, so NOTHING is listed, never every authorization unchecked) and `checkOrgConnections` pings each one, at most `ORG_CONNECTION_CHECK_CONCURRENCY` (5) at a time, the whole listing bounded by `ORG_CONNECTION_LISTING_TIMEOUT_MILLISECONDS` (60 s: an org still unanswered then is `notConnected`, never the list). `checkOrgConnection` never throws: a scratch org whose `isExpired` is exactly `true` (core works it out from the saved `expirationDate`) is `expired` with no request; an authorization core could not read (`error` set) or whose username `isValidTargetOrgIdentifier` refuses is `notConnected` unpinged; anything else is `Org.create({ aliasOrUsername: username })` then `refreshAuth()` (the `HEAD` request `sf org list` pings with; its connection refreshes an expired access token and SAVES it to the CLI's own auth file, as any connection does), raced with `ORG_CONNECTION_CHECK_TIMEOUT_MILLISECONDS` (20 s), and only a resolved ping is `connected`; an `Org` that opens under another username than the one asked for (`Org.create` resolves an alias first) is `notConnected` unpinged. A listing whose own time ran out answers with `isComplete: false` and is NOT cached, so the next picker checks again. There is no Dev Hub `ScratchOrgInfo` query (a decision on #502): a deleted scratch org fails its ping and is `notConnected`, so the `deleted` reason is no longer produced, though the type and counts keep it. A ping asks nothing else of an org: never `logout`, delete or any change (a test proxies the `Org` and holds it to `refreshAuth`). The answer is cached for the extension host's life; two pickers during one check share it; a FAILURE is never cached; `refreshConnectedOrgAuthorizations` (the Treecipe tab's ⟳, and an org the extension creates) replaces the answer, sharing a check already in flight rather than starting a second, and a generation bump keeps a check started before a clear from writing over it. The cache records the authorization usernames read BEFORE the check (`checkedAuthorizationUsernames`): an authorization added since is checked again rather than reported not connected, and a quick pick (no ⟳) that a cached answer leaves empty asks again once — otherwise the warning's own advice, `sf org login web` and try again, could never work. An org is labelled by its own authorization's alias, else its username (the CLI-answer alias fallback went with the CLI). Error text shown in a notification goes through `escapeForNotification`. A suite that lists orgs answers the pings with `SalesforceOrgService/tests/OrgConnectionPings.ts` (`answerOrgConnectionPings`, from `mocks/orgConnectionPings.json`). Quick picks go through `VSCodeWorkspaceService.promptForAuthenticatedOrgDetailOnceListed`, which opens busy with nothing selectable until the listing answers. The Treecipe tab's picker drops its list and selection BEFORE a check, so nothing can be selected or inserted in mid-check, and a stale answer is discarded by `dataOrgRequestSequence` — but it stays DRAWN (#305): the dropdown, ⟳ and + New scratch org stay visible and enabled, a `dataOrgSpinner` sits right of the dropdown, the dropdown's ONE option carries no index (the change handler posts only an all-digit value), and every tree's reason is `RECIPE_COCKPIT_ORG_CONNECTION_CHECK_INSERT_REASON`. That option is `RECIPE_COCKPIT_ORG_LOADING_PLACEHOLDER` until the host posts `dataOrgProvisional` — the org chosen last, else the default, read by `readLocalDataOrgDetail` from the local authorization files AFTER the listing has started, so it never delays the check — which the panel drops for another model, an older check, or once the list arrived. ⟳ stays clickable mid-check; the host joins the check in flight. Once ⟳'s listing answers, the describes of every org it listed are dropped (`clearDescribeCacheForOrg`, #537), and every clear bumps `describeCacheGeneration`, so a describe asked for before it never puts its answer back. While a run holds the selection (`describeSelectionHoldingRun`), `refreshDataOrgs` and `loadDataOrgs` are answered with `dataOrgListingRefused` naming it, never silence: the panel cleared its picker on the click, and `holdDataOrgPickerBeforeCheck`'s snapshot puts it back, but only once every listing it asked for is answered (`dataOrgUnansweredListingCount`), since an earlier ⟳ the host accepted has already dropped its list. No run lock is force-released from the panel; each is released in its run's `finally`. Insert Data Set's free-text alias box is gone: it is a picker like the others
- **`SalesforceOrgLogin` holds the two browser logins, and is the one place the extension WRITES the workspace's default org** (#630) — the reader picks the login on the confirmation, as "+ New scratch org" offers the CLI or the library. Both take only a login address `normalizeLoginUrl` accepted: `https://test.salesforce.com` or an `https://*.my.salesforce.com` origin with no port, path, query or user name, so a typed address can never send the OAuth request to another host. Both answer the same `OrgLoginOutcome`, naming the username and nothing else; a failure message is one line cut at 300 characters, because it can be the browser request's own `error_description`. Both SAVE the authorization before the browser has fetched its success page, so `cancelled` and `timedOut` can leave an org authorized: neither is ever worded as "nothing was authorized". `ORG_LOGIN_TIMEOUT_MILLISECONDS` is 5 minutes for both.
  - **Why two:** 3.198.0 had only the in-process login. The file it saves is the same as the CLI's, but the access and refresh tokens are encrypted with a key from the keychain the PROCESS's environment selects (`SF_USE_GENERIC_UNIX_KEYCHAIN`, `secret-tool` on Linux, the macOS keychain). VS Code started from a Dock or launcher often has a different environment from the reader's terminal, so an org the cockpit authorized could not be used by `sf` in that terminal. The CLI login is offered first and is the one to use when `sf` must work; the library login stays for a machine with no CLI on VS Code's PATH, and for a remote window, where it is VS Code that opens the browser on the reader's own machine.
  - **`authorizeWithSalesforceCli`** runs `sf org login web --instance-url <address> --no-prompt --json` through `SalesforceCli.runSalesforceCli` (listed in `SalesforceCliCallSites.test.ts`). The workspace is NOT passed as its working directory: it starts in the extension host's own folder, as the other non-project calls do. That is not a guarantee that no `sfdx-project.json` is read, since VS Code launched from inside a repository on macOS or Linux starts there, but `--instance-url` overrides `sfdcLoginUrl`, and a project's `oauthLocalPort` only moves the localhost callback, which the default connected app's fixed redirect refuses. Project mode, with its absolute `sf`, was not used: it skips every PATH entry inside its working directory, so a neutral folder such as the home folder would miss a CLI installed under it (`~/.npm-global/bin`). The login address is DNS labels only (`HOST_NAME_LABEL_PATTERN`), since WHATWG `URL` keeps `"`, `&` or `'` in a host and on Windows the address reaches the CLI through cmd.exe, where a `"` makes `quoteWindowsArgument` throw. A login the CLI had finished when a cancel arrived is answered `authorized`; an answer over `maxBuffer` says so. `--no-prompt` keeps the CLI from waiting on a question nobody can see. No `--alias` or `--set-default`. The CLI opens the browser itself. The caller's cancel kills the process (and with it the port 1717 listener), and the timeout is `runSalesforceCli`'s, which kills it too. `readLoginAnswer` reads the `--json` answer as untrusted text that ALSO HOLDS THE ACCESS TOKEN: only `status`, `name`, `message` and `result.username` are read, stdout is never quoted, a `PortInUseError` is `portInUse`, ENOENT says the CLI is not installed or not on PATH, and a success needs `status: 0` AND exit code 0 and a username `isValidTargetOrgIdentifier` accepts.
  - **`authorizeWithCoreLibrary`** runs `@salesforce/core`'s `WebOAuthServer` in VS Code (no `sf` process). The caller opens the authorization address (the cockpit: `vscode.env.openExternal`), which carries the client id, state and code challenge, never a token. Core's server has no public stop and no timeout, so a cancel, the timeout and every other ending close its private `webServer` in a `finally`: left listening it would hold port 1717 and refuse the next login with `PortInUseError`. That reach into a private member is the one coupling to core's internals; it is optional-chained, so a core that renames it only loses the early close, and `SalesforceOrgLoginCoreServer.test.ts` asks the real, un-mocked class for `webServer.close` without listening on a port, so a core bump that renames it fails a test. The caller's `openLoginPage` is raced against the cancel and the timeout too, so a browser that never reports back cannot outlive them.
  - Neither login sets an alias: `setAlias` (`StateAggregator.aliases.setAndSave`, its failure answered as a message, not thrown) is the caller's to run once it knows the org is a sandbox or scratch org, so an alias never lands on, or moves to, a production org. `writeWorkspaceTargetOrg` sets `target-org` in `<workspace>/.sf/config.json` directly rather than through core's `Config`, which resolves the project from `process.cwd()`: `.sf` must pass `SfdxProjectService.isPathContainedInWorkspace` (so a linked `.sf` is refused), `config.json` must be a regular file under 1 MB holding a JSON object, a new file is written `wx`, and every other key is kept. Before #630 the extension only read this file, and "+ New scratch org" still creates with `setDefault: false`.

What CLAUDE.md's Project Structure said about these files before #563 trimmed it to one line each.

    │   ├── SalesforceOrgService.ts           # Shared @salesforce/core connection helper, session-cached connected-org listing (each authorization pinged in process with `Org.refreshAuth()`, at most 5 at a time, #502, listConnectedOrgAuthorizations) behind every org picker, authorizations read fresh (`StateAggregator.clearInstance()` first, #286), session-cached describe (cleared whole, or per org username and object after a permission set assignment) + pure describe normalization, the Organization IsSandbox/OrganizationType query, the CLI's default target org read in process (`readDefaultTargetOrgIdentifier`, listed first by `listDataOrgDetails(workspaceRoot)`, read locally by `readLocalDataOrgDetail`), the Dev Hubs a scratch org can come from (`listDevHubOrgDetailsForPicker`: `isDevHub === true` and connected, the default first), the default Dev Hub read in process (env, project .sf/config.json, global), and the local authorization per username (`readScratchOrgDetail`, #458, #499: `AuthInfo.create({ username }).getFields()`, never `getFields(true)`, no process and no network, so not cached; scratch org or not and its expiration date only) for the Target Org Manager's type label
