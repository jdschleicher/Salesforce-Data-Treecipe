# Relationship trees — design notes

Design notes moved out of CLAUDE.md (#563). Read this before changing the service; CLAUDE.md keeps only the rules every change must follow. History is in CHANGELOG.md.

- **Several selected record types are several BLOCKS of one object, and only the first carries friends** (#194) — `RecordTypeSelection.buildRecordTypeBlocks` decides them: none or one selected is ONE block under `<Object>_NickName` (so the output is #193's, byte for byte), several are one block each, in selection order, nicknamed `<Object>_<DeveloperName>_NickName` (a reserved nickname, the self-lookup iteration's, takes `_RecordType_NickName`). `DirectoryProcessor` writes the first block into `FullRecipe` and the rest into `ObjectInfo.AdditionalRecordTypeRecipes` (set only when there are several), reading the fields again per block (`buildAdditionalRecordTypeRecipes`) so `Fields` and every relationship stay the first block's. `RelationshipService` writes the later blocks right after the first: flat, or nested at the same depth with the same ancestors. Friends, and the self-lookup iteration, go under the FIRST block only (a decision on #194: every block would multiply the children's records; #622's option copies the friends, never the iteration), and `readNickname` of `FullRecipe` is what every wired lookup and #189 lower-level wiring names. A lookup still the REFERENCE ID REQUIRED TODO to a parent with several blocks gets a `### TODO -- RECORD TYPE BLOCKS --` comment line under it (`annotateLookupsToRecordTypeBlocks`), never an edit of the lookup line, which #151's wiring matches exactly; a self-lookup never lists its own block. The Recipe Cockpit reads each later block as an occurrence told apart by nickname. A child's blocks are SIBLING friends of one object type, which `FakerJSRecipeProcessor` names `<YAML nickname>_<parent>` instead of `<Object>_<parent>` (only when a sibling shares the object type), because records sharing a nickname share a `referenceId` and the insert resolves a nickname to the first record holding it
- **With `isChildTreeCopiedPerRecordTypeBlock` on, every record type block carries its own copy of the object's children** (#622) — `RecordTypeSelection` holds the option (off by default, so #194's first-block-only rule and its output are unchanged), and `DirectoryProcessor` hands it to `generateSeparateRecipeFiles`. One walk, `buildBlockPlacer`, decides where every block is written and under which ancestor blocks, for both layouts, so a copy is the same copy in a faker-js and a snowfakery recipe and neither backend has a path of its own. A later block's friends are a COPY: each nickname written in it becomes `<nickname stem>_<copying block's stem>_NickName` (`Contact_NickName` under `Account_Partner_NickName` is `Contact_Account_Partner_NickName`), one name per (copy, nickname), memoised so the block that writes it and every lookup that names it agree; a name the tree already holds takes `_Copy` before `_NickName`. Every part is a nickname built from api names joined by `_`, so a copy name passes `SalesforceApiName`. A lookup in a copy is wired to the ancestor BLOCK it sits under, and a #189 lower-level parent to its record in the same copy when that parent is a friends-descendant of the copied object, else to the original. The option applies at every level, so a child with blocks of its own is copied with all of them and each of its blocks copies the grandchildren. **A self-lookup iteration stays under the object's first block only** (decided on #622): it is the object's own parent-and-child pair, not part of a record type's children, and copying it per block would add self-lookup records nobody selected; a child copied into a later block still carries ITS iteration, under its first block in that copy, wired to the copy. faker-js nests copies under `friends:` and needs no processor change: a copy is a friend with its own YAML nickname, wired through the ancestor map like any other. Snowfakery stays flat (`buildFlatTreeRecipeWithChildCopies`): each child is written once per placement, level by level after its parents, and a lookup to an ancestor block — only a line that is exactly the generated TODO — becomes `${{reference(<nickname>)}}`, Snowfakery's link to the latest record with that nickname (checked under Snowfakery 4.2.1); every other lookup keeps its TODO and #194's block note. A flat tree with no later block that has children goes through `buildCombinedTreeRecipe`, byte for byte
- **A standard field with no `<referenceTo>` takes its parent from ONE static map, and only then** (#400) — `StandardFieldParentReferenceMap` (imports nothing, no prototype, own-key check) names the parent of `Account.ParentId`, `Contact.ReportsToId`, `Case.ContactId` and the rest by `Object.Field`. `DirectoryProcessor.applyStandardFieldParentReference` reads it for a Lookup, MasterDetail or Hierarchy field only when the XML has no `<referenceTo>` AND no custom relationship mapping names the field, so both still win (a mapped HIERARCHY field takes the mapping's parent as its `referenceTo`, because a Hierarchy's recipe value is decided by `referenceTo` alone); the answer is held to `SalesforceApiName` and set as the field's `referenceTo`, so it reaches the object map through `addKeyToObjectInfoMap` like any `<referenceTo>`. `RecipeService` writes a Hierarchy field WITH a parent as its backend's `lookup` value and one without as before ("FieldType Not Handled"), so an unmapped Hierarchy (`User.ManagerId`) is unchanged. The lookup type lists read `'Hierarchy'` (they read `'Hiearchy'` before #400, so no Hierarchy field ever reached a relationship). Never add a polymorphic field (`WhoId`, `WhatId`, `OwnerId`): one parent cannot be named. A new entry is a decision pinned in `StandardFieldParentReferenceMap.test.ts`
- **A faker-js tree nests its children under `friends:`; a snowfakery tree stays flat** (#46) — `DirectoryProcessor` turns nesting on from the faker service INSTANCE that writes the object recipes, not by reading the configuration again. Each object is still written once; it is nested under its CLOSEST parent that has a recipe (deepest level, ties by `<`), and only a parent at a strictly LOWER level qualifies, so the chosen parents are a forest whatever cycles the lookups contain. A lookup to ANY ancestor on the chain is written as that ancestor's nickname — only a line that is exactly `RelationshipService.referenceIdRequiredTodo` — and so is a lookup to a NON-ancestor parent that has a recipe in the same tree at a strictly LOWER level, because a lower level is inserted first (#189); `wireLookupsToParents` decides both. Every other generated lookup TODO in a nested tree — a parent with no recipe, a cycle (same or higher level, a self-lookup's top iteration included) — gets ` -- <Parent>` appended, so the TODO says what it needs. `FakerJSRecipeProcessor.resolveNonAncestorNicknameReferences` resolves the non-ancestor nicknames AFTER the whole recipe is generated, so document order does not matter: a field whose value is exactly an entry's YAML nickname, and that the ancestor map did not already resolve (`_ancestorResolvedFieldNames`, carried per friend), is pointed round-robin, in generation order, at that entry's records, never at itself. Insert resolves a nickname to the FIRST record holding it, and an entry with `count > 1` and no friends gives every record one nickname, so only for an entry a reference names those records are renamed `<nickname>_<n>`, skipping names already held — a data set nothing names is written exactly as before. Those records have no friends, which is what makes renaming them safe; a change that renames a record with friends breaks every child's ancestor reference. An object with a SELF-lookup gets ONE more friend, last in its `friends:` block: itself again, nicknamed `<Object>_child_NickName`, every self-lookup wired to the iteration above because it is passed as its own ancestor, and carrying no friends of its own, so nothing recurses (#188). That puts a parent and its child in one `collectionsApi-<Object>.json`, which is why `CollectionsApiService.partitionRecordsIntoInsertRounds` inserts a file in rounds: a record naming another record of the SAME file waits for the round that inserts it, and a file with no such reference is one round, the request it always was. The Recipe Cockpit tells two occurrences of one object apart by NICKNAME, never by api name: the scan records `nicknames` and `parentHeaderIndex`, `parseRecipeSource` keeps a later occurrence as an `iterations` entry on the first only when each carries a nickname no other occurrence does (else first-wins, as before), and every writer operation takes an optional `objectNickname`; without one, an object written twice is still refused. A tree where nothing nests goes through `buildCombinedTreeRecipe` unchanged, byte for byte. Two consumers make the wiring true at run time and both must stay: `FakerJSRecipeProcessor` hands each friend a `Map` of every ancestor's YAML nickname to the nickname of the record it is generated under (not only the direct parent's — with `count > 1` a grandchild's top-parent lookup would otherwise name no record), and `CollectionsApiService.updateLookupReferencesInCollectionApiJson` replaces a JSON string only when the WHOLE string is a nickname, because a friend's generated nickname CONTAINS its parent's (`Contact_Account_NickName`) and a substring replace rewrote the friend's own `referenceId`. The DirectoryProcessor suites load `objectInfoWrapper.RecipeFiles` — what is written — and `generatedRecipeYaml` holds every nested object to the flat recipe's fields apart from the wired lookups
- **A lookup cycle is cut at the lookup that closes it in a name-order walk; a level is the longest path from a root over what remains** (#104) — `calculateRelationshipLevels` walks the tree once, depth-first. It starts from the roots (no parent but itself) in name order, then from any object not yet reached in name order, and takes children in name order, all sorted by code unit. A lookup to an object already on the walk's path closes a cycle and is left out (`walkCuttingCycleClosingLookups`); what remains has no cycle, so one pass in reverse finish order (an insert order) gives each object the longest path from a root. A cycle has no insert order that satisfies every lookup in it, so exactly one lookup per cycle has to stay a TODO, and this picks it by name alone. The levels then never depend on map order or on how many paths reach an object, and every other lookup in the cycle is wired as it would be without one. Equal levels for a whole cycle (strongly connected components) were rejected because they make every lookup in the cycle a TODO, the common `Account ⇄ Contact` pair included. The walk this replaced visited an object once per path (7,174,452 calls on 42 objects in 14 layers), and in a cycle reached by two paths it climbed again by map order. For a graph with no cycle the two agree, and `RelationshipService.levelsDifferential.test.ts` holds that against the old walk on 600 seeded graphs
