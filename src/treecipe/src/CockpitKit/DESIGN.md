# Cockpit kit — design notes

Design notes moved out of CLAUDE.md (#563). Read this before changing the service; CLAUDE.md keeps only the rules every change must follow. History is in CHANGELOG.md.

- **The elements every cockpit panel draws with are a kit module, `panel/CockpitPanelElements.ts`** (#638) — `createElement`, `createButton` (typed by `CockpitButtonKind`, and still checking a kind at run time against `COCKPIT_BUTTON_KINDS` for callers in a string), `setShown`, `isMotionReduced`, `setShownWithMotion` and `drawToggle`, plus `SVG_NAMESPACE`. They replace `COCKPIT_KIT_CREATE_BUTTON_SCRIPT` and `COCKPIT_KIT_BUTTON_KINDS_SCRIPT`. The confirmation imports them, `focusElement` included (#657). The reveal and conceal timings are `CockpitMotion.ts`, which imports nothing, so a cockpit's stylesheet and the kit's motion use the same numbers.
- **The confirmation's panel half is a checked module, `panel/CockpitConfirmDialogPanel.ts`** (#637) — it was the `COCKPIT_KIT_CONFIRM_DIALOG_SCRIPT` and `COCKPIT_KIT_CONFIRM_LABELS_SCRIPT` strings. A cockpit takes it by bundling it (the Recipe Cockpit's `panel/RecipeCockpitPanel.ts` exports `renderConfirmRequest` and `closeConfirmDialog`). The kit cannot import a cockpit, so a cockpit calls `connectConfirmDialog` once when its panel starts (#657), with what the dialog posts through, the model on screen, where it draws, what it makes inert behind it and the chevron's view box and path; using the dialog before that throws and says so. `confirmDialog` is the module's own `let`, and `isConfirmDialogOpen` is what a cockpit's own dialog asks. `CockpitKit.test.ts` fails when the module `declare`s anything, or the Recipe Cockpit routes a message before it connects the dialog. The labels and answer shapes are in `CockpitConfirmLabels.ts`, which imports nothing, so the bundle never pulls in `crypto`; `CockpitConfirmDialog.ts` re-exports them.
- **A confirmation can offer record type set modes, and the answer names one** (#623) — a request carrying `recordTypeSetModes` (`{name, label}` each, with `recordTypeSetModeLegend`) draws a `radiogroup` between the body and the buttons, one `check`-kind button per mode with `role="radio"`, the first chosen, all in the Tab cycle. Modes that are not all a name and a label draw none. A chosen button answers `recordTypeSetMode: <name>`; Cancel names none. `CockpitConfirmDialog.readRecordTypeSetMode` gives the name back only when it is one the request offered, and the cockpit that asked reads any other answer as Cancel. Labels are the host's and written with `textContent`. Slice D of #620 offers a second mode through the same group.
- **A dropdown a reader can search or choose from is a kit module, `panel/CockpitSearchableSelect.ts`** (#678) — `buildSearchableSelect` draws a `createButton('secondary')` with `role="combobox"` that opens a popup: a `type="search"` box, a line inviting a choice, and a `listbox` of the labels it was given (`drawOptions(labels, selectedIndex)`), or nothing to open (`drawPlaceholder(text)`, and while `setDisabled(true)`). It knows nothing of what the labels name and calls `onSelect` with an INDEX only. A choice changes nothing on screen until the cockpit draws it with `drawOptions`: a cockpit can refuse a choice without answering (the Recipe Cockpit's host does while an insert or a prompt holds the org), and a button that drew the choice itself would then name an org nothing writes to. The search filters, ignoring case, the labels already drawn; Up and Down move the highlight (`aria-activedescendant`), Enter chooses, Escape closes with focus back on the button and stops there, so a dialog around it is not cancelled, Tab closes it with focus back on the button so a dialog's focus trap moves on from there (the search box is never in a trap: it is hidden while closed), a redraw or a run that closes it while the reader types puts focus back on the button, and a click outside closes it through one capturing document listener shared by every dropdown, since only one is open at a time. Every label and the no-match text go in through `textContent`. Its styles are `panel/CockpitSearchableSelect.css`, in the cascade after `CockpitOrgPicker.css`; the popup's `z-index` stacks only inside what holds it (the pinned org section or a dialog). The Recipe Cockpit's Target Org Manager is its first user; the Picklist Cockpit (#525) reuses it.

## Files

What CLAUDE.md's Project Structure said about these files before #563 trimmed it to one line each.

```
    ├── CockpitKit/                          # What every cockpit shares (#524, epic #523): the --sdt-* palette, button kinds (createButton, and its CSS as `panel/CockpitButtonKinds.*.css`, the pieces the Recipe Cockpit's stylesheet includes where they were), org picker and pinned section CSS (`panel/CockpitOrgPicker*.css`), the in-panel confirmation (`panel/CockpitConfirmDialog.css`, markup, its panel half as a checked module in panel/ (#637), and the names and classes it needs from the cockpit beside it, each list derived and held by a test; buildConfirmationId/readAnswer); imports only crypto
```
- **The kit's styles are `.css` files under `panel/`, and the values they read are custom properties** (#644) — `COCKPIT_KIT_STYLESHEET_FILES` lists them in cascade order; a cockpit includes each from its own `.css` with an include line where its rules belong, and `esbuild.panel.js` inlines them into that cockpit's one `<style>`. The kit's style strings and `buildStyles()` are gone. A value the TypeScript reads too is never written in a `.css` file: `COCKPIT_KIT_CUSTOM_PROPERTIES` names the five (`--sdt-motion-reveal`, `--sdt-motion-conceal`, `--sdt-spinner-rotation`, `--sdt-pinned-org-section-scroll-padding`, `--sdt-action-card-height`), built from the constants, and `CockpitKitStylesheet.buildCustomProperties` writes them into `:root` beside the palette. `CockpitKit.test.ts` fails when a `.css` file under `panel/` is not listed, when the Recipe Cockpit's stylesheet does not hold each once and in order, and when a kit `.css` holds a `${` or a timing outside a `var()`.
