# Recipe Cockpit — design notes

Design notes moved out of CLAUDE.md (#563). Read this before changing the service; CLAUDE.md keeps only the rules every change must follow. History is in CHANGELOG.md.

## Gate, doors and the shell

- **The Recipe Cockpit ships behind a workspace feature flag, and the COMMAND HANDLER is the gate** — every slice lands on main enabled by `salesforce-data-treecipe.recipeCockpitEnabled`, which `openRecipeCockpit` checks before a panel is created and which a modal warning is the only thing that writes. It is a runtime check rather than a `when` clause on the palette entry, because hiding a command hides it from the palette and from nothing else: a keybinding, a task or another extension can still execute it by id. Gating at the point the panel is created is also what saves every later slice a flag of its own — a cockpit nobody opted in to has no panel, hence no model built, no message posted and no rendered value for a panel action to have been derived from. The warning's link to the tracked work is a BUTTON (`View Known Issues`), because a VS Code dialog renders its detail as plain text and has no clickable link in it, and choosing it RE-SHOWS the warning rather than ending the command — a dialog closes on whichever button is clicked, so opening a browser would otherwise leave the reader to re-run the command to answer what they went to research. The url is a LABEL QUERY (`recipe-cockpit`) rather than issue numbers, which go stale as slices split, and it belongs to the dialog and never to the panel: the shell's `default-src 'none'` would render a link there dead, and interpolating any url into the template is the first step back toward a markup context the builder has none of. The flag is written at WORKSPACE scope, so opting in on one project says nothing about the next, and a dismissed warning writes nothing
- **The cockpit's version and CHANGELOG link are the HOST's, and the link opens ONE constant** (#333) — the title row is `.cockpitHeader` in the shell, with `#cockpitMeta` at its right OUTSIDE `#cockpitBody`, so no load, empty state or failure to draw removes it; the panel script fills it once at start (`renderCockpitMeta`: a `<button class="cockpitChangelog">` holding the GitHub mark AND the version span, so a click on either opens the CHANGELOG and its `aria-label`/`title` add the version once one arrives (#487), then, since #350, the ? `helpToggle`, in that order, both 2rem tall, ? drawn pressed by CSS on `[aria-expanded="true"]` while the help is open, and the help section's own ✕ (`helpClose`) and Escape closing it as ? does (`closeHelp`: saves the place, focus back to ?), one `flex-wrap: nowrap` group pushed right by `margin-left: auto` so it wraps as a whole; ? is the SAME button for every model, `disabled` with no `aria-expanded`/`aria-controls` while the body holds no help section (before the first model, after a failure to draw, `disableHelpToggle`), and `renderHelp` enables it and builds only the section. The cockpitChangelog button holds the GitHub mark, `RECIPE_COCKPIT_GITHUB_GLYPH_PATH`, built with `createElementNS` and filled from `--sdt-muted`/`--sdt-accent`). The version is read once in `activate` (`RecipeCockpitService.setExtensionVersion(context.extension?.packageJSON?.version)`), kept only if `RECIPE_COCKPIT_EXTENSION_VERSION_PATTERN` accepts it, carried on `IRecipeCockpitPanelState.extensionVersion` only then, and posted as its own `extensionInfo` message FIRST in `buildReplayMessages`, so the recipe model did not change and a replay with no version is exactly what it was. The panel writes it with `textContent`. A click posts `openChangelog` with NOTHING else; the router routes it before any model (there is no rendered value for it to come from) and reads nothing from the message, and `openChangelogInBrowser` hands `RECIPE_COCKPIT_CHANGELOG_URL` to `openExternal`, a refusal or throw being one fixed warning. The URL never goes into the shell — `default-src 'none'` would make it a dead link and the external-asset test allows only the SVG namespace — so a link out of the cockpit is always a message to the host, never an `href`
- **The Recipe Cockpit's shell builder takes a nonce and nothing else, and that signature is the guarantee** — `buildWebviewShellHtml` interpolates the nonce and compile-time constants defined in its own file (the palette among them), so the document carries no value this extension does not author. Recipes and org describes come from sources it does not control: they reach the panel over `postMessage` and are written through `textContent`, which is why the builder needs no escaping rather than having escaping that can be forgotten. A value from outside the file can only reach the template through a PARAMETER, so widening the signature to take a model is the single edit that re-opens the markup context — the same reason `localResourceRoots` is `[]` rather than omitted, which is what actually denies the grant (omitting it defaults to the extension directory plus every open workspace folder). `routePanelMessage(message, panelState)` is the whole host half of the protocol as a pure function returning an ACTION rather than a reply, so every allow-list decision is asserted without a webview and the side effects live in one executor; a command that carries a payload type-checks it and MATCHES it against an allow-list built from the rendered model, never validates it as a path. The panel is a singleton revealed rather than duplicated, its document rebuilt with a fresh nonce per load and its message subscription disposed before it is replaced — two listeners answering one `ready` is one acknowledgement the panel never asked for
- **The Recipe Cockpit's ? help and `docs/RECIPE-COCKPIT-GUIDE.md` say the same thing, and the guide's url never reaches the panel** (#332) — the help's text is `RECIPE_COCKPIT_HELP_SECTIONS` (four sections) and `RECIPE_COCKPIT_HELP_BACKEND_NOTE`, injected as constants and written through `textContent`; the section is the first thing in the body (there is no toolbar row since #548), starts collapsed, and is drawn in the empty state too. Its live summary (`describeTreeDifferences`) counts only tree fields the model already carries, so a new kind of selection on the tree model belongs there. **Open the full guide** posts `openHelpGuide` with nothing else; the router routes it once any model is posted, and the host opens `RECIPE_COCKPIT_HELP_GUIDE_URL` with `openExternal` — the url is never in the shell, the model or a message. `RecipeCockpitHelp.test.ts` fails when the guide's `##` headings differ from the help's or a picture is missing or over 200 KB. Pictures come from `developmentSupportScripts/recipe-cockpit-screenshots/captureRecipeCockpitScreenshots.js` (the real shell, the historyWorkspace fixture, an already-installed Playwright, no new dependency); `/cockpit-help-sync` updates both and re-takes them after a cockpit change. Whether the section is open is the place's optional `isHelpExpanded`

## What the cockpit loads and draws

- **The Recipe Cockpit traverses what Generate Treecipe WROTE, not a second derivation of it** — the objects wrapper (`treecipeObjectsWrapper-<ts>.json`) is the source of objects and fields, and the run's `.yml` files are the source of line numbers, read by the one layout `RecipeService` emits for BOTH backends (`- object:` at column zero, `  fields:`, one field per four-space line, and every column four spaces deeper per `friends:` level in a nested faker-js recipe) — so there is no per-backend reader to drift. `parseRecipeSource` reads through `RecipeCockpitRecipeWriter.scanRecipeObjects` rather than a copy of it, so the line the panel jumps to and the line an edit changes are one scan's answer. Runs are ordered by the timestamp SUFFIX, never the folder name: `recipe-fakerjs-` sorts above `recipe-` whatever the dates, and the fixture is shaped so that regression fails. Fields the recipe carries and the wrapper does not (standard-field mappings, the record type line — they never become a `FieldInfo`) are listed and marked `isOnlyInRecipeFile`, because a wrapper-only view says `Account` has no `Name`. A recipe path becomes something the host OPENS, so each passes `SfdxProjectService.isPathContainedInWorkspace` before it is kept; the model carries the path once per OBJECT and only a line number per field. Allow-lists have two generations: PENDING is built when a model is posted and only the panel's `rendered` — echoing that model's `renderSequence` — promotes it to ACTIVE, and every `ready` (each reveal reloads the document) empties ACTIVE — a post succeeding says nothing is on screen, and an ack of an OLDER model must not activate a newer one's targets. An object the wrapper holds with no `Fields` is a lookup target that `RelationshipService` still lists in `RecipeFiles.objects`; it is kept only if a recipe file carries its `- object:` line. A filter never HIDES an object: one with no match stays, collapsed and labelled, because a hidden one reads as "not in the recipe". Rows are built on first expand and a filter auto-expands at most `RECIPE_COCKPIT_AUTO_EXPAND_OBJECT_LIMIT` objects AND at most `RECIPE_COCKPIT_AUTO_EXPAND_ROW_BUDGET` rows (an expand builds every row, and an object can have 800 fields), so a keystroke's cost is bounded by what it expands rather than by what it matches. Containment is re-checked when a source is OPENED, not only when the model is built. There is no render ceiling: 12,000 fields posts 4.05 MB and 120,000 posts 40.67 MB (CHANGELOG 3.25.0) — re-measure when #57 adds per-row diff data; 3.31.0 re-measured with 50-value picklists on a third of the fields: 5.99 MB at 12,000 and 59.94 MB at 120,000, with values loaded on expand
- **The Recipe Cockpit describes an org only for the tree insert, and only objects the HOST rendered** — the one describe left after #266 is the insert readiness's, for the objects of the confirmed-drawn model's trees in the org the Treecipe tab selected (see the org picker bullet). Object names come from workspace files and jsforce puts them in the describe URL PATH unencoded, so `describeObjects` refuses anything that is not an api name (`isUsableObjectApiName`) before any request, and the connection is opened by USERNAME so it names the org the cache key does. The answer is posted only if the model it described is still on screen, and the panel re-checks `renderSequence` — a describe of one run is never drawn over another's rows. Only a per-object SUMMARY is posted; the normalized field model lives in `SalesforceOrgService`'s session cache, keyed by org USERNAME (an alias can be re-pointed) and object, which a repeat request answers without connecting at all. Failures are never cached, and one object the org lacks is that object's outcome rather than the request's; a failed CONNECTION is the request's. `SalesforceOrgService.getConnection` is the one `Org.create` that hands out a connection (`requestOrgFrontDoorUrl`, #501, makes its own because it needs the `Org` for `refreshAuth()`, `checkOrgConnection`, #502, makes one per authorization only to ping it with `refreshAuth()`, and `ScratchOrgService.runScratchOrgSetupWithLibrary`, #507, opens the Dev Hub's `Org` for `scratchOrgCreate`) — `CollectionsApiService.getConnectionFromAlias` delegates to it. `normalizeDescribeResult` is pure and type-checks everything, because the describe came over the network
- **The Compare tab and the recipe-vs-org metadata diff are GONE** (#266, slice D of #261) — `RecipeCockpitMetadataDiff` and its suite and mocks, the panel's `selectOrg`, the host's `orgDescribe`/`orgProgress` messages, `describableObjectApiNamesByTreeKey`, `orgDescribeMessagesByTreeKey`, the reopen carry (`carryOrgDescribeMessages`, `buildComparedRowsSignature`), the diff's host-only copy of the recipe's picklist values (`picklistValuesByObjectApiName`; the display copy, `picklistDisplayValuesByObjectApiName`, stays), the per-card status filter, the Compare rows and their CSS, and the `required in <org>` note an unticked field drew from a comparison. The router routes nothing for a posted `selectOrg`, and a saved place or `focusTree` naming the tab opens the card on Treecipe (`RECIPE_COCKPIT_REMOVED_TREE_TABS`). The insert's own readiness still refuses an unticked field the org requires. There is no Regenerate recipe button (#263): a run is regenerated with Generate Treecipe from the palette. The no-run empty state's **Generate Treecipe** button (#214) goes through `generateTreecipeAndReload`, which executes the unflagged `treecipe.generateTreecipe` — whose handler RETURNS its promise so the cockpit can reload the run it wrote — stays in flight (`isGenerateTreecipeInFlight`) until the RELOAD finishes, and reloads even when generation FAILED, because the panel's disabled button comes back only through a render. It posts no payload and is routed only while `isGenerateTreecipeOffered` is set, a pending/active flag set at post for a model with no run and promoted on `rendered`. A run that could not be read, or a run with no trees, offers no button.
- **The Recipe Cockpit is relationship-tree cards, with Treecipe and Previously Used Data Sets tabs on each; the Classic flat list is GONE** (slice 8, #181: its view, its DOM, its filter and every message, allow-list and function that served only it) — `buildRecipeTreeViewModels` makes one card per `RecipeFiles` entry, in that order, KEYED by the folder Generate Treecipe wrote the tree to (`RelationshipService.buildRecipeTreeFolderName`, the one rule both use — never the position, which renumbers). A card lists its objects in insert order by NAME and carries no field rows of its own: every card that lists an object draws the one posted field model, so a tree adds a few names per object to the payload. Lookups come from `RelationshipDetail.parentObjectToFieldReferences`, filtered to parents in the SAME tree (the tree's whole object list, lookup targets with no recipe included); a self-lookup is drawn as `(ParentId)`. A wrapper with no or an empty `RecipeFiles` falls back to one card per recipe `.yml`, objects in file order, no lookups, and `RECIPE_COCKPIT_TREE_DATA_MISSING_NOTICE`; an object no card claimed gets a `Not in a relationship tree` card, because leaving it out reads as "not in the recipe". `fieldTypeWithSize` is formatted HOST side (`formatFieldTypeWithSize`) from the `length`/`precision`/`scale` Generate Treecipe now records on each `FieldInfo` only when the XML has them (`FieldInfo.applyFieldSize`), so an older run, or a field with no size, serializes and draws exactly as before; `fieldType` stays bare. Picklist values are POSTED FOR DISPLAY, but per row on expand — a row carries only `isPicklist`, the panel posts `loadPicklistValues {objectApiName, fieldApiName}`, and the host answers from `picklistDisplayValuesByObjectApiName` only for a key in `loadablePicklistKeys`, a pending/active allow-list like the others (built at post, promoted on `rendered`, emptied on every `ready`, on a new post and on a failure to draw). Posting them with the model measured 96.17 MB at 120,000 fields with 50 values per picklist, past the 60 MB the issue set; on expand it is 59.94 MB (55.47 MB before this slice — the rest is the faker expressions, which list every value). Values are written with `textContent`, and no search box searches them, because the panel does not have them until a row is opened. There is NO global find box and no 🔍 (#217): every tab of every card has its own search box (`buildTabSearch`), whose text lives in `treeState.searchQueries` and whose element stays in the tab's panel, so it survives a tab switch and a collapse and a new model starts it empty. Each matches only what its tab draws: Treecipe (`applyStructureFilter`) against ONE lowercased haystack per field (`searchTextOf`: names, label, controlling field and faker expression, shared by every occurrence of an object) plus the sized type the row draws; Previously Used Data Sets the data set folder name and its own name; the Treecipe search also narrows the Record types section's rows by object, record type and restricted field (#321). Treecipe never hides an object (one with no match stays collapsed with "no matching fields") and auto-expands under the `RECIPE_COCKPIT_AUTO_EXPAND_*` limits, spent PER SEARCH BOX (`expandMatchesWithinBudget`); the data sets tab hides the rows that do not match and counts what is left. A search never switches the tab it was typed in. The panel's own name-keyed maps (`objectsByApiName`, `pendingPicklistValueElements`) are `Object.create(null)`, because an object named `__proto__` in a hand-edited wrapper otherwise vanished from its card. Tree DOM uses its own class names (`treeCard`, `treeObject`, `treeField`, …). There is no view switch: a card's tabs are `RECIPE_COCKPIT_TREE_TABS` — Treecipe · Previously Used Data Sets · Troubleshooting · Query · Treecipe Adapter, Treecipe selected, the data sets tab only for a card with a history, Troubleshooting, Query and Treecipe Adapter only for a card with a folder (#346, #367, #415) (Record types, #195, is a section of the Treecipe tab since #321, drawn only for a card listing an object with two or more record types) — and a `focusTree` can name any of them (an insert and Add friend reload onto `treecipe`; `readTreeFocus` accepts only `datasets` from the panel). The Previous Versions tab is GONE (#265): its rows, the `loadVersionSummaries`/`versionSummaries` and `diffTreeVersion` messages, their `summaryTreeKeys`/`diffKeys` allow-lists, the host handlers and the per-run wrapper field-count cache
- **The Treecipes section draws ONE card, chosen in a dropdown, under one search across every card** (#374) — the section's FIRST row is the Generate Treecipe run list (#533, `buildRunPicker`: a `<label for="runSelect">` of `RECIPE_COCKPIT_RUN_PICKER_LABEL`, then `runSelect`, posting `selectRun` as before); its label reads **Select Generated Treecipe runs by date:** (#548); there is no toolbar row since #548, and a run with no trees, or one that could not be read, draws the run row at the top of the body above its notice. **Favorites only** and its count sit on the Treecipe dropdown's row, to its right (`buildTreePicker` calls `renderFavoritesToggle`, only when a card has a folder). Every card is still built into the document by `renderTree` (class `treeCard hidden`) and only the dropdown's choice (`selectedTreeKey`) is shown, by `applyTreePicker`, so a card keeps its tab, searches and opened objects while another is on screen, and `datasetAdded`, `treePreferences` and `objectSelection` reach a card whether or not it is drawn. A card's body is built the first time it is chosen (`setTreeExpanded`), and the draw itself posts nothing; a READER's pick or result click on a card's Treecipe tab posts `loadDataOrgs`, as opening a card did. The header neither folds nor draws a `▸`. Under the dropdown, `treePickerObjects` (#385) names the shown card's objects in insert order, each once (no iteration), an excluded one marked `(excluded)`/`(auto-excluded)` in text, redrawn by `drawTreePickerObjects` only when the card on screen changes or its `objectSelection` does, hidden with no card. The dropdown (`treePickerSelect`, option values are indexes into `treePickerTreeStates`, never names) lists the cards Favorites only leaves, in `RecipeFiles` order, narrowed to the section search's matches; the card on screen stays listed first with `RECIPE_COCKPIT_TREECIPES_SEARCH_NO_MATCH_OPTION_SUFFIX` when it does not match, and no match disables the dropdown. `focusTree` goes through `chooseTree` before it applies. The section search (`treecipesSearch`, its own classes so a tab's `tabSearchInput`/`tabMatchCount` lookups never find it, with the #373 magnifier) matches card titles and folders, object api names, field api names and labels (`Object.field` only for a query with a dot) and record type developer names — the model carries no record type label — from an index lowercased ONCE per model on the first query (`buildTreecipesSearchIndex`, dropped on a name or star change), draws at most `RECIPE_COCKPIT_TREECIPES_SEARCH_RESULT_LIMIT` `link` buttons grouped by card and kind with one `N more` line, all through `textContent`; a click (`openTreecipesResult`) chooses the card on its Treecipe tab and opens one object, scrolls to a field's row (clearing the Treecipe tab's search and checks when they hide it) or opens the Record types section through `applyTreeFocus`. The place's optional `selectedTreeKey` (written only when not the first card) and `treecipesSearchText` are read by `applyPlaceBeforeRender` and `normalizePanelPlace`, so the place version did not change; a saved per-card `isExpanded` is ignored. Measured at 12,000 fields: 8–9 ms for the first keystroke, 1.4 ms after (CHANGELOG 3.113.0)
- **An action that only ADDS a data set updates the panel in place, and the allow-list rule still holds** (#226) — the tree insert posts `datasetAdded {treeKeys, dataset, renderSequence, updateSequence}` instead of reloading, so the org selection and readiness stay on screen. The data set is placed by `RecipeCockpitTreeHistory.buildAddedDataset`, which runs the one folder through `groupTreeHistories` — the reload's own rule — and answers `undefined` (the caller reloads) for a folder that is not a data set name, not inside the workspace, unreadable or on no card. The host adds it to the STORED model (a reveal's replay draws it) and its names to a COPY of the pending history allow-lists (`cloneTreeHistoryAllowLists`): once a model is acknowledged pending and active are the SAME sets, so adding in place would offer Open/Insert… before the row is drawn — a test fails if the copy is removed. Only `partialRendered` echoing the latest `updateSequence` over the model on screen promotes it (`activateDatasetActions`), and only once that model's own `rendered` has arrived: `acknowledgedRenderSequence` is set by `activateActions` and cleared by `ready`, a new post and a failure to draw, so a forged or late ack never activates a model no document drew. The panel drops a `datasetAdded` for another `renderSequence`, adds the row at the top of a BUILT Previously Used Data Sets tab (`insertBefore`, search re-applied; a tab built empty is rebuilt to get its search box), and touches no other node — a test compares every node of every other card by identity. Reset Selections, Add friend and a run switch still reload. Measured in CHANGELOG 3.60.0: 3.40 MB → 862 bytes at 1,000 objects
- **The Recipe Cockpit keeps the reader's place in `vscodeApi.setState`, and spends it ONCE** (#222) — `retainContextWhenHidden` stays off, so a hidden tab's document is thrown away and the host replays the model on `ready`; what the READER did lived only in the page. The panel saves NAMES only (run, scroll offset, whether the Target Org Manager's org picker was in use, and per card: opened by the reader, tab, each tab's search as typed (`searchTexts`), Treecipe objects expanded by api name + nickname, open picklist rows, and whether the Record types section is expanded as the optional `isRecordTypesExpanded`; neither the Target Org Manager nor the Treecipes section folds, #355, #364), never a path, value or org. `readSavedPanelPlace` reads it once at script start inside a `try`; `takeRestorablePlace` spends it on the document's FIRST `recipeData` and applies it only when `selectedRunFolderName` matches, and nothing is saved before the place is spent (or the default draw would overwrite it). A LATER model in the same document of the run already on screen (a generate, the tree insert, Add friend reloading it) takes the place on screen instead (`takeSameRunPlace`, built by the same `buildPanelPlace` as a save) BEFORE `resetPanelState` drops it, and restores it the same way (#225); another run, or a model after a failed draw (`renderedSequence` null), starts fresh. Everything that asks the host (a picklist row, the org picker) is restored AFTER `rendered`, beside `focusTree`, which is applied after the restore and so wins; a picker the reader never used still lists no orgs. `savePanelPlace` is skipped while `isRestoringPlace`, so a restore saves once. A restore never posts `loadDataOrgs` by itself. The place is version 2 (#255): a version 1 place is read through `RECIPE_COCKPIT_TREE_TAB_RENAMES` (`structure` → `treecipe`, `dataByOrg` → `compare`, selected tab and search keys), by `normalizePanelPlace` and by the panel's `upgradePlace`, rather than dropped. A place of EITHER version can name a tab since removed (`RECIPE_COCKPIT_REMOVED_TREE_TABS`, `versions` since #265, `compare` and `dataByOrg` since #266, `recordTypes` since #321, applied after the renames on both sides; a card saved on `recordTypes` also opens with the Record types section expanded): its card opens on Treecipe, its search is dropped rather than moved onto another tab, and `expandedVersionRunFolderNames`, `statusFilter` and `expandedDataObjectApiNames` are no longer in the shape, so they are ignored. Removing another tab is adding its name to that list; the place version did not change. A picklist's open state is on the FIELD (`isPicklistExpanded`). Every saved field is type-checked and name-keyed lookups have no prototype; `RECIPE_COCKPIT_PANEL_PLACE_VERSION` is the shape, and a place of another shape is not read. Re-running **Open Recipe Cockpit** on an open panel for the same workspace reloads the run on screen (`loadRecipeRunByRuns` falls back to the newest when it is gone), keeps `dataOrgRequestSequence`, and carries no comparison, since there is none (#266). The same place is ALSO kept in `context.workspaceState` (`RECIPE_COCKPIT_PANEL_PLACE_STATE_KEY`, #230) so it survives a close and a window reload: every `savePanelPlace` posts `savePlace`, routed only for the run of the confirmed-drawn model and written at most once per `RECIPE_COCKPIT_PANEL_PLACE_PERSIST_DELAY` (500 ms) — never only on dispose, since a reload may not run `onDidDispose`, which flushes what is waiting. A panel opened with nothing to carry reads it through `normalizePanelPlace` (field-by-field, run a plain folder NAME, only the shape's fields kept, so no path, value or org is ever written), requests that run, and hands it over as `restorePlace` on the POSTED copy and every replay until that model's `rendered`; a run that is gone or a place that cannot be read is removed and the newest run opens. The panel's own `getState` wins over it. There is NO `WebviewPanelSerializer` and no `onWebviewPanel:` activation event, on purpose: a reload must never load a run or contact an org on its own, and a test asserts both
- **Switching runs ASKS about the tree selections before the next run is drawn** (#399) — selections are keyed by tree FOLDER, so a tree of the next run with the same folder took them over unseen. `selectRun` passes `confirmRunSwitchSelections` to `loadRecipeIntoPanel` as `confirmBeforeRender`, which runs after the run is read and before `renderRecipeModel`. It asks only when the run differs from the one on screen and `listFolderNamesWithStoredSelections` (excluded objects, unticked fields, counts or validation-rule unticks of the trees ON SCREEN) is non-empty, through `confirmInPanel` with `RECIPE_COCKPIT_RUN_SWITCH_RESET_LABEL` and, only when a tree of the next run has one of those folders, `RECIPE_COCKPIT_RUN_SWITCH_APPLY_LABEL`; the detail names the folders and how many trees match, and says a missing object or field is ignored. Apply writes nothing; Reset re-reads the selections, deletes every on-screen folder (a folder not on screen keeps its own) and writes, and a failed write keeps the run on screen. Cancel, or a load a newer one replaced, renders nothing: the current load posts `runSwitchCancelled`, which puts the panel's dropdown back on `renderedRunFolderName`, and the status line is cleared before the question. The router's `selectableRunFolderNames` check is unchanged, and pins and edited expressions are in the recipe file, so neither choice touches them

## Orgs: the Target Org Manager

- **The Treecipe tab's org picker names an org only by INDEX, checks only what the rendered trees list, and COUNTS NOTHING** (#238, #255) — no `SELECT COUNT()` is sent anywhere in the cockpit: an org-wide count is not a fact about a tree, and a tree-scoped view of org data is a separate design. ONE panel-wide org selection (select, type label, Open in browser, ⟳, + New scratch org) is drawn ONCE, in the panel's **Target Org Manager** section right under the ? help section (#348; #255 had drawn a view of it at the top of every card's Treecipe tab, and no card draws one now), and every tree card sits in a **Treecipes** section below it. Both are drawn only when the run has trees (the org section only when some card has a `runFakerRecipeFileName`). NEITHER folds (#355 for the org section, #364 for Treecipes, reversing #348): `buildStaticCockpitSection` draws both headers with no toggle and no listener, and a 3.98.0+ place's `isOrgSectionCollapsed` and `isTreecipesSectionCollapsed` are ignored by the panel and dropped by `normalizePanelPlace`, so the place version did not change. The org section is PINNED (#364): `#cockpitOrgSection` is `position: sticky; top: 0` on its own opaque light tint, `--sdt-org-section` (#433, a token apart from `--sdt-header` so a retuned header never recolours it), with a `z-index` above every other layer, and `html:has(#cockpitOrgSection)` carries `scroll-padding-top` (`RECIPE_COCKPIT_PINNED_ORG_SECTION_SCROLL_PADDING`) so a row scrolled into view stops below it; the ? help is not pinned. Pinning is CSS only: an `overflow` other than `visible` on any ancestor of `#cockpitOrgSection` would quietly undo it. The picker is still a VIEW (`buildDataOrgView`, `dataOrgViews`, drawn from panel state by `drawDataOrgViews`), now of exactly one. A selection's readiness is held panel-wide (`dataOrgReadinessByObject`, `dataOrgReadinessByTreeObjectKey`) and decides each tree's insert, built or not. A connection failure, or an org that is not a sandbox, rides on `dataOrgSelection` as `failureMessage`, which the panel keeps on screen and uses as every tree's insert reason when no readiness follows.  the host posts the authorized orgs as LABELS (`dataOrgList`); the panel posts back `selectDataOrg {orgIndex}`, an integer index into the list the host holds (`dataOrgDetails`), so no username or alias ever comes from the panel and none is posted to it. The objects checked are `collectDataOrgObjectApiNames` of the confirmed-drawn model (`dataOrgObjectApiNames`, pending/active like the other allow-lists: promoted on `rendered`, emptied on `ready`, a new post and a failure to draw). ## Recipe writes

- **The Recipe Cockpit writes a recipe by patching LINES, never by round-tripping YAML** — both backends emit recipes as template strings, and the `### TODO` comments in them carry meaning (which record type to pick, which lookup needs a reference) that `js-yaml` drops on `dump`, so a load-and-dump is lossy by construction. `RecipeCockpitRecipeWriter` is pure and imports NOTHING (a test fails if it gains an import): text in, text plus an `edit` or a typed refusal out. It holds to the same layout contract `parseRecipeSource` reads — the reader IS its `scanRecipeObjects` — and every line outside the touched field's own lines is byte-identical afterwards, line ending included — new lines take the ending of the line they follow, and a missing final newline stays missing. The READER takes the first occurrence of an object or field, which is right for jumping to a line and wrong for changing one, so the WRITER refuses a duplicate object, field, `fields:` block or property rather than guessing which the reader meant. A friend under `friends:` (#46) is the same contract shifted: `scanRecipeObjects` keeps the open objects as a stack, one per level, the object at depth d has its `- object:` at column 4d and every other column (`getObjectLayout`) four spaces deeper per level, and a `- object:` line opens a friend ONLY one level down and only inside its parent's `friends:` block — anywhere else it is an unrecognized line, as it always was. A value handed to `insertField`/`replaceFieldValue` is written as for a top-level object and its continuation lines are moved to the friend's depth, so no caller has to know the depth. `commentOutField` is the removal because it is reversible: the lines sit at the FIELD column (four spaces at the top level) under a `### TODO -- RECIPE COCKPIT -- FIELD COMMENTED OUT -- <field> -- <n> lines` marker (deeper would read as the previous field's continuation), their encoding has one inverse, and `restoreCommentedOutField` gives the original back byte for byte. The COUNT is what bounds a restore — without it a reader's own comment directly below read as more of the field — and restore refuses unless those lines are still exactly what was written — which is why the reader treats a comment at field depth or shallower as ending the FIELD and not the BLOCK. The `yaml` package's comment-preserving `Document` API was the alternative; it is a new runtime dependency and re-flows `${{ }}` scalars, so it would still need every fidelity test. Values and names are validated so no argument can add a line the layout would read as another field or object — and that includes the line breaks the JS split does not see: PyYAML (snowfakery's reader) breaks at U+0085, U+2028 and U+2029, so a value carrying one is refused rather than split. Every call scans the whole file, so bulk edits need a one-scan batch entry point before a slice applies them. `insertFriend` (#197) is the one operation that ADDS an object: it copies the friend's own block from the occurrence above a self-lookup iteration (never its `friends:`), one level deeper, with a nickname no occurrence holds and every value that was the top occurrence's nickname re-pointed at the iteration's, and it reads its result back through `scanRecipeObjects` before answering. `listInsertableFriendObjectApiNames` is what the cockpit's **+** offers, so the panel and the writer share one answer — `parseRecipeSource` calls it for EVERY iteration at every load, so it takes the `buildScannedFriendIndex` built once per scan and must never walk the whole scan per call (that was 18 s at 11,000 objects); it also refuses a copy carrying a lone CR or U+0085/U+2028/U+2029, since text after one would keep its old column; the panel posts `addIterationFriend` with four NAMES, matched against `insertableFriendTargets` (pending/active, keyed by tree, object, nickname and friend, mapped to the host-only recipe file), and the host asks in a modal, writes and reloads focused on the card's Treecipe tab

## Acceptance journeys

- **A journey drives the cockpit as a reader does and records what it does, so a refactor can prove the UX did not change** (#577, slice A of #576) — `tests/acceptance/RecipeCockpitJourney.ts` opens the real host through `openRecipeCockpitPanel` with only `vscode` and `@salesforce/core` faked (`RecipeCockpitJourneyFakes.ts`), on a fresh temp copy of a fixture workspace. Messages go through the real `routePanelMessage` and executor one way and into the real panel script in `RecipeCockpitPanelHarness`'s fake page the other, until both sides are idle: both queues are empty and every host handler has finished or is waiting on a prompt only the next step can answer. It records notifications, quick picks and input boxes with what each offered, files written or removed under the workspace, calls on the fake org and the message log in both directions. The fakes are plain functions rather than `jest.fn`, because `restoreMocks` would wipe a `jest.fn`'s implementation between the tests of a journey opened once. A journey also gets its own empty home folder and no `SF_TARGET_ORG`-style variables, because the org listing reads the CLI's default org from both: the orgs it offers are the fixture's on every machine. The home folder is a `jest.spyOn(os, 'homedir')` made again at every step, not a `HOME` assignment: `os.homedir()` asks the operating system rather than Jest's copy of `process.env`, and `restoreMocks` removes a spy before each test of a suite that opened its journey once.
- **`screen()` is an accessibility-style tree (role, name, state), not the page's text or markup** — #565 reshapes the markup, and roles and names are what a reader goes by. A role is the `role` attribute or the element's own; a name is `aria-label`, `aria-labelledby`, `<label for>`, then the text inside; what the shell's own stylesheet sets to `display: none` is not on screen (`isDisplayed` in the panel harness, which is the only place that knows a class). `AcceptanceSelectorScan.test.ts` fails on any lookup by class or id in `tests/acceptance/`.
- **Every action is a named step, and so is every expectation of a journey** — a failure reads `Step "choosing "Lead-ONLY" … › choose the treecipe "Lead-ONLY"" failed: …` and says in the reader's words what was on screen instead. An action checks its own visible effect: `chooseTree` reads the card shown (its "Rename …" button), never the dropdown's value, which is what the reader just set whether or not the card followed it; `chooseRun` needs a new model drawn for that run. `JourneyCatchesBreakage.test.ts` breaks the cockpit two ways (the Treecipes dropdown's change listener removed, `selectRun` refused) and requires the first journey to fail naming the step.
