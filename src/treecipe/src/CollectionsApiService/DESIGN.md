# Collections API insert — design notes

Design notes moved out of CLAUDE.md (#563). Read this before changing the service; CLAUDE.md keeps only the rules every change must follow. History is in CHANGELOG.md.

- **A referenceId with no nickname resolves by WHOLE value, never inside a record's own referenceId** (#622) — a snowfakery record carries no nickname, so `SnowfakeryRecipeProcessor` writes its referenceId as `<Object>_Reference_<row id>` alone, and `readNicknameFromReferenceId` finds nothing to match. A recipe that copies children per record type block writes the child's lookup as that same text (`Account_Reference_${{reference(<nickname>).id}}`), so `updateLookupReferencesInCollectionApiJson` also replaces a JSON string value that IS such a referenceId (`nicknamelessReferenceIdPattern`), with a lookbehind that skips a value of `"referenceId"` and a lookahead that skips a key. `Account_Reference_2` never matches inside `Account_Reference_21` because the match is the whole quoted string. It is ONE pass over the file with a `Map` lookup; a pattern per inserted record took 15 s on a 10k-record file. Any field whose whole value is such a referenceId is rewritten, not only a lookup -- the same as a nickname match. `partitionRecordsIntoInsertRounds` and the Recipe Cockpit's same-file check still read nicknames only, so a nickname-less reference to a record of the SAME file is not deferred to a later round: the generator never writes one (a flat recipe has no self-lookup iteration), only a hand-written recipe could
- **A file that stops the shared insert is a red ERROR with View errors** (#310) — `upsertDataSetToSelectedOrg` shows `Failed to process <file>: …` through `VSCodeWorkspaceService.showNotificationWithWorkspaceFile('error', …)` (the helper the cockpit's notifications use too), whose **View errors** (`INSERT_VIEW_ERRORS_LABEL`) opens that attempt's results file after re-checking it exists and is in the workspace. A request that THROWS is recorded in that file by `recordRequestFailure` (one `REQUEST_FAILED` entry with the `fileName` under the object's `FailureResults`, never counted as a failed record by `isRequestFailureResult`), so the first file throwing still leaves a file to open; a write that fails leaves the error without a button. A caller that reports the outcome itself passes `isFailureReportedByCaller` and gets no notification from here. A cancel stays a warning
