# VS Code workspace services — design notes

Design notes moved out of CLAUDE.md (#563). Read this before changing the service; CLAUDE.md keeps only the rules every change must follow. History is in CHANGELOG.md.

- **The status bar item is a second DOOR to `treecipe.openRecipeCockpit`, never a second code path** (#251) — `package.json`'s only activation event is `workspaceContains:treecipe/treecipe.config.json`, so a Treecipe workspace activates at window load and every other workspace activates on a command as before. `VSCodeWorkspaceService.registerRecipeCockpitStatusBarItem` (from `activate`) creates `$(list-tree) Treecipe` on the left (id `salesforce-data-treecipe.recipeCockpit`, name `Treecipe Recipe Cockpit`, so the status bar's own hide menu labels it), tooltip `Open Recipe Cockpit`, whose `command` IS the palette's command id, so the feature-flag gate, the opt-in warning and the singleton reveal all apply to a click. Showing it does NOTHING else — no run, no org, no `sf`, no webview — which is what keeps "a reload never loads a run or contacts an org" true now that a reload activates. It is created only while `showRecipeCockpitStatusBarItem` is not `false` (default `true`) and a folder is open, followed live through `onDidChangeConfiguration` (hide, then show the same item), and the item and listener are pushed to `context.subscriptions`. Because activation now runs on every load, `activate` writes `useSnowfakeryAsDefault` only when the workspace does not already hold `false` (read with `getWorkspaceScopedExtensionConfigValue`), so `.vscode/settings.json` is not rewritten per load. An activation event is a static glob: a config kept elsewhere through `treecipeConfigurationPath` gets no item at load, and since every contributed command also activates the extension, any folder gets the item once a Treecipe command has run
- **A workspace-scoped config write can REJECT, and the answer is a boolean rather than a thenable nobody holds** — `setExtensionConfigValue` is `async` and returns whether the write landed, because VS Code refuses a `ConfigurationTarget.Workspace` write in a window with no folder open and an unawaited `update()` turns that into an unhandled rejection: nothing written, nothing reported, and the caller proceeding as though it had succeeded. That is invisible for a setting nothing reads back and the whole defect for one a user was just asked to choose. It reports the setting and the reason itself, for the call sites buried in paths with nothing to say to a user; the callers that CAN act on the answer do. Two do: `openRecipeCockpit` refuses outright when there is no workspace (the guard `openPicklistDependencyExplorer` already uses — a cockpit with no workspace has no recipe to traverse and no scope to record an opt-in at), and that guard comes BEFORE the flag check rather than after: the flag is WRITTEN at workspace scope but READ through the merged configuration (default < user < workspace) and is contributed in `package.json`, so a User-scope value would otherwise answer `true` in a folderless window and hand back a cockpit with nothing to render — a mutation test pins the order. It still opens the panel but says the workspace will ask again if the write fails for another reason; `activate` writes `useSnowfakeryAsDefault` only when a workspace folder exists, since warning a user about a setting they never chose is what writing unconditionally produced
