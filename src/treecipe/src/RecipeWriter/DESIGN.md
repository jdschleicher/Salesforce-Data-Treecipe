# Recipe writer — design notes

`RecipeCockpitRecipeWriter` imports nothing, so it sits at layer 0 (#572) and `RecipeService` and the Recipe Cockpit both import it without importing each other. The class keeps its cockpit name. Read this before changing the writer.

## Writing a recipe

- **The Recipe Cockpit writes a recipe by patching LINES, never by round-tripping YAML** — both backends emit recipes as template strings, and the `### TODO` comments in them carry meaning (which record type to pick, which lookup needs a reference) that `js-yaml` drops on `dump`, so a load-and-dump is lossy by construction. `RecipeCockpitRecipeWriter` is pure and imports NOTHING (a test fails if it gains an import): text in, text plus an `edit` or a typed refusal out. It holds to the same layout contract `parseRecipeSource` reads — the reader IS its `scanRecipeObjects` — and every line outside the touched field's own lines is byte-identical afterwards, line ending included — new lines take the ending of the line they follow, and a missing final newline stays missing. The READER takes the first occurrence of an object or field, which is right for jumping to a line and wrong for changing one, so the WRITER refuses a duplicate object, field, `fields:` block or property rather than guessing which the reader meant. A friend under `friends:` (#46) is the same contract shifted: `scanRecipeObjects` keeps the open objects as a stack, one per level, the object at depth d has its `- object:` at column 4d and every other column (`getObjectLayout`) four spaces deeper per level, and a `- object:` line opens a friend ONLY one level down and only inside its parent's `friends:` block — anywhere else it is an unrecognized line, as it always was. A value handed to `insertField`/`replaceFieldValue` is written as for a top-level object and its continuation lines are moved to the friend's depth, so no caller has to know the depth. `commentOutField` is the removal because it is reversible: the lines sit at the FIELD column (four spaces at the top level) under a `### TODO -- RECIPE COCKPIT -- FIELD COMMENTED OUT -- <field> -- <n> lines` marker (deeper would read as the previous field's continuation), their encoding has one inverse, and `restoreCommentedOutField` gives the original back byte for byte. The COUNT is what bounds a restore — without it a reader's own comment directly below read as more of the field — and restore refuses unless those lines are still exactly what was written — which is why the reader treats a comment at field depth or shallower as ending the FIELD and not the BLOCK. The `yaml` package's comment-preserving `Document` API was the alternative; it is a new runtime dependency and re-flows `${{ }}` scalars, so it would still need every fidelity test. Values and names are validated so no argument can add a line the layout would read as another field or object — and that includes the line breaks the JS split does not see: PyYAML (snowfakery's reader) breaks at U+0085, U+2028 and U+2029, so a value carrying one is refused rather than split. Every call scans the whole file, so bulk edits need a one-scan batch entry point before a slice applies them. `insertFriend` (#197) is the one operation that ADDS an object: it copies the friend's own block from the occurrence above a self-lookup iteration (never its `friends:`), one level deeper, with a nickname no occurrence holds and every value that was the top occurrence's nickname re-pointed at the iteration's, and it reads its result back through `scanRecipeObjects` before answering. `listInsertableFriendObjectApiNames` is what the cockpit's **+** offers, so the panel and the writer share one answer — `parseRecipeSource` calls it for EVERY iteration at every load, so it takes the `buildScannedFriendIndex` built once per scan and must never walk the whole scan per call (that was 18 s at 11,000 objects); it also refuses a copy carrying a lone CR or U+0085/U+2028/U+2029, since text after one would keep its old column; the panel posts `addIterationFriend` with four NAMES, matched against `insertableFriendTargets` (pending/active, keyed by tree, object, nickname and friend, mapped to the host-only recipe file), and the host asks in a modal, writes and reloads focused on the card's Treecipe tab

- **The writer reads a recipe's `RecordTypeId` blocks for the cockpit AND Run Faker** (#621) — `IRecipeRecordTypeBlocks`, `buildEmptyRecordTypeBlocks` and `collectRecordTypeBlocks` moved here from `RecipeCockpitService`, which now calls them here, so `ExtensionCommandService` can read them without importing the cockpit. A block written as the DEFAULT carries the RecordType Options TODO under its `RecordTypeId`; `listChosenRecordTypesByObject` keeps only objects no block wrote that way. An object with exactly one record type is written with no TODO, so its data set names it: its records do carry it. A test holds every golden recipe, generated with no choice, to an empty answer.

## Files

```
    ├── RecipeWriter/
    │   ├── RecipeCockpitRecipeWriter.ts      # Pure line-level recipe patcher (insert / replace / comment out / restore a field, pin a fixed value on every occurrence and put the pinned lines back (#342), set nickname or count, cut one object's block for a readiness field check, add a friend under a self-lookup iteration, wire a TODO lookup to a nickname, add a lookup's standard parent from a template and wire it, list every empty lookup to one parent with why Create or an org record is refused (#421), build the Treecipe Adapter's one-object value recipe (#417), build the filtered copy the generate button generates from when objects are excluded, fields unticked or counts set, count a recipe's records per object) with typed refusals; imports nothing
    │   └── tests/                            # RecipeCockpitRecipeWriter.test.ts; its recipe fixtures stay in RecipeCockpitService/tests/mocks/recipeWriter/, which the cockpit suites also read
```
